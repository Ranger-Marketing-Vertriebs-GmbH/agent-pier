# Live Push Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the browser's REST polling with one WebSocket per tab (`GET /api/live`) that pushes each topic's data, keeping only justified, slow, visible-only polls.

**Architecture:** A server `LiveHub` (`server/features/live/`) computes each topic once per access scope, coalesces invalidations, and sends `snapshot`/`state`/`delta`/`same` frames with revisions; row topics reuse `ChatSync` and `applyListSync`. A per-tab `LiveClient` (`web/lib/live/`) owns the socket, the hidden-tab policy and the poll fallback; `useLiveTopic` returns the `useResource` shape so call sites change in about one line. Phase 0 fixes hidden-tab polling without the channel; Phases 1-5 move topics into the channel in order.

**Tech Stack:** Node.js ESM, Express, `ws`, React 19 hooks, `node:test`, fast-check, Playwright (`page.routeWebSocket`).

**Spec:** `docs/superpowers/specs/2026-10-27-live-push-design.md` (read it with this plan; the `#n` poll numbers refer to its inventory).

## Global Constraints

- Branch `feat/live-push` in `.worktrees/live-push`. All six phases ship in **one pull request** at the end; no release between phases. Every task leaves `npm run check` green. Do not push until the final task.
- Node `^22.23.4 || ^24.22.1 || >=26.12.1`. No new dependency; use the existing `ws`. No permessage-deflate on `/api/live`.
- Every source and test file stays at or under 600 lines (`npm run check:structure`). Extract a module instead of growing a file past it; `server/features/requests/request-broker.js` (589), `server/application/services.js` (471) and `server/app.js` (451) are close.
- Per socket: at most 64 topics, inbound messages ≤ 4 kB (`maxPayload: 4096`), topic ids ≤ 200 characters; at most 16 live sockets per principal. An unknown `op` closes with 1008. Above 256 kB `bufferedAmount` a newer frame replaces the queued frame of the same topic; above 2 MiB close with 1013. Server shutdown closes live sockets with 1012.
- Coalescing: trailing debounce 150 ms, `maxWait` 1 s, and a `running`/`again` loop so the last change always gets one recompute. A recompute whose digest is unchanged sends nothing.
- `maxBytes` per frame: default 256 kB, `state` 128 kB; over it the client gets `stale` and does one GET of the existing route.
- Client: backoff 0.5 s → 30 s with jitter; app ping every 25 s; fallback to the previous poll (visible-only, previous interval) after **three** failed handshakes, while it keeps retrying the socket; on `visibilitychange → hidden` unsubscribe sampled topics at once; close the socket after 5 minutes hidden or on `pagehide`; on `visible`/`pageshow`/`online` reconnect and resubscribe with stored revisions or cursors.
- Server samplers run only while subscribed: `session.models` 3 s (nudged by native activity), `session.requests` startup prompts 1.5 s only inside the startup window, `state` tools and PATH utilities 60 s, `connections.problems` and the remote update check at most every 60 s, `system.status` 5 s.
- Remaining browser polls, all through `startVisiblePolling`: system status 5 s (until Phase 5), AgentBus peers and messages 10 s, Codex MCP OAuth 3 s only while pending, editor file metadata 15 s and on focus, CLI account auth 30 s, login status 60 s until Task 1.7, then 5 min and on focus.
- Access: a restricted user reaches only topics in `userTopics` (all `me.*`); every other topic answers her exactly like an unknown topic. Payloads are computed per `scopeKey`, never shared across scopes.
- No hidden-tab requests in any phase, including Phase 0. Writes stay REST. REST read routes stay; only the SSE routes `/api/assistant-events`, `/api/inbox/events` and `/api/me/events` go in Phase 4.
- UI follows `docs/ui-guide.md`; no new UI copy is planned. Any copy that appears goes into `web/lib/i18n/de/` and `web/lib/i18n/en/` with matching keys, then `npm run i18n:confirm` and the updated `translation-lock.json` in the same commit.
- `web/lib/live/live-topics.js` imports nothing browser-only or i18n, because the Node test stub imports it.
- Tests: `node:test` with `node:assert/strict`, fast-check for properties, Playwright for the browser; integration tests use `applicationFixture` (disposable data dir, private tmux socket), never the default tmux server or real user sessions.
- Commits: English, prefixes `feat:`/`fix:`/`chore:`, each ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. A restricted user subscribing to an owner topic id (with or without a parameter, over 200 characters, with odd Unicode) must get a frame byte-identical to an unknown topic's. Test in Task 1.2.
2. `/sessions/<id>/requests` carries a relative `interaction.age`, so a naive digest changes on every read and sends a frame per sample. Unchanged requests must send nothing, and the cross-device guard must still expire. Test in Task 1.6.
3. A tab hidden during a handshake, restored from bfcache (`pageshow` with `persisted`), or woken after laptop sleep must end with exactly one socket, its topics resubscribed with `have`, and no requests while hidden. Test in Task 1.3.
4. After a server restart (1012, new `instance`), a client holding an old revision or ChatSync cursor must get a full snapshot, never a delta against a lost baseline. Tests in Tasks 1.1 and 1.2.
5. Fixture specs whose REST mocks change mid-test must still see updates through the shared live stub, and a spec that closes every `/api/**` socket must reach its data through the fallback without hanging. Test in Task 1.4.

**Interfaces:**

- Produces:

```js
// TopicDefinition
{
  name: string,                 // "state", "session.requests"
  param?: RegExp,               // topic id is `${name}:${param}` when set, else `name`
  mode: "state" | "rows" | "signal",
  authorize(principal, param): boolean,
  scopeKey(principal, param): string,      // "owner", `user:${id}`
  read(principal, param): unknown | Promise<unknown>,   // not called for "signal"
  watch?({ param, invalidate, nudge }): () => void,      // change sources
  sampleMs?: number,
  sampling?(param): boolean | Promise<boolean>,          // sampler runs only while true
  digest?(value): unknown,      // what is hashed for change detection; default: value
  maxBytes?: number,                                     // default 262144
}
class LiveHub {
  constructor({ debounceMs = 150, maxWaitMs = 1000, timers = { setTimeout, clearTimeout }, onError })
  instance: string                                       // randomUUID per process
  define(definition: TopicDefinition): void              // duplicate name throws
  resolve(principal, topicId: string): { definition, param } | null   // null: unknown, unauthorized, too long, bad param
  subscribe(principal, topicId, have: { instance?, revision?, cursor? } | undefined, send: (frame) => void): () => void
  reauthorize(): void                                    // sends {type:"revoked", topic} and drops subscriptions that no longer pass
  close(): void
}
```

- Frames (server → client): `{type:"snapshot", topic, revision, data}`, `{type:"state", topic, revision, data}`, `{type:"delta", topic, revision, data}`, `{type:"same", topic, revision}`, `{type:"changed", topic, revision}`, `{type:"stale", topic, revision}`, `{type:"revoked", topic}`. `revision` is the instance's integer counter; `rows` frames carry the `ChatSync.encodeScoped([topicId, scopeKey], listRows(value), cursor)` result as `data`.
- Subscribe answer: state mode → `same` when `have.instance === hub.instance && have.revision === revision`, else `snapshot`; rows mode → encode against `have.cursor` (only when `have.instance === hub.instance`): `delta` when the cursor is in the baseline, `same` when that delta is empty, else `snapshot`; signal mode → `same`, then `changed` on each change.
- Instances are keyed by `topicId + "\0" + scopeKey`; `watch` and the sampler start with the first subscriber of an instance and stop with the last.

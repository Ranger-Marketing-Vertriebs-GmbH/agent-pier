# Pipelines and task profiles

Pipelines run a task through reusable CLI stages such as implementation, review and verification. They use AgentPier's existing accounts and native Codex, Claude Code and OpenCode installations. No separate Docker runtime, provider-key store or CLI installation is required by this feature.

## Profiles

Open **Pipelines → Profiles** to create or edit a task template. A profile chooses an existing account, its CLI, permitted models and a default model, native permissions, role instructions and a kickoff prompt. Account selection also selects the configured provider and its credentials. An empty model selection leaves the account or native CLI default in control; it is not a claim that a particular model was confirmed.

Profiles can be enabled, disabled, duplicated and grouped by refinement, planning, implementation, review or maintenance. Built-in planner, spec writer, implementer, code reviewer, security reviewer, UX reviewer, UI reviewer, approver, conflict resolver, bug hunter and app tester profiles are editable starting points, as are the built-in pipelines **Implement and review** and **Software factory** (see [Software factory](#software-factory)). Deleting or changing them persists across restarts; see [Built-in profiles and pipelines after an update](#built-in-profiles-and-pipelines-after-an-update).

Text parameters use `{{parameter_name}}` in the kickoff prompt. Standalone profile sessions validate required parameters and reject undeclared values before launch. Pipelines require enabled autonomous profiles without required parameters, because a pipeline supplies the overall task rather than an interactive parameter form. Role instructions are included in the native prompt.

The selected permission mode applies to standalone profile sessions. Pipeline stages have no terminal operator and always use autonomous permissions, including retries and resumed turns: Codex receives `--dangerously-bypass-approvals-and-sandbox` (YOLO) and `--dangerously-bypass-hook-trust`; Claude receives `--permission-mode bypassPermissions`; OpenCode receives `--auto`. OpenCode's explicit deny rules still apply. Native account/provider capabilities and context limits still apply. See [providers](providers.md) for endpoint and model restrictions.

Pipeline CLIs run with the host user's file permissions, without an AgentPier-enforced OS sandbox, and report `AGENTRUNNER_SANDBOX=none`. This variable describes the run; it does not configure permissions. Only start pipelines for workspaces and hooks you intend to authorize. Explicit human approval stages and `requiresHuman` verdicts still pause the pipeline; autonomous tool permissions do not skip these decisions.

### Built-in profiles and pipelines after an update

An update brings new built-in profiles and pipelines to an existing installation once. When AgentPier loads its pipeline definitions, it adds every built-in item it has not offered before, unless an item of that kind already exists, and records it in `seedsApplied` in `pipelines/definitions.json`. A built-in profile or pipeline you deleted is therefore never added again. A built-in pipeline whose profiles you deleted is not added either. Definitions written before this record existed count the original nine built-in profiles and **Implement and review** as offered, so a deleted one stays deleted; every newer one is added once.

Built-in profiles whose role text changed are updated only when you have not edited that text: a stored profile whose role is still exactly the text an earlier version shipped gets the current text (and its description too, when it still equals the old role), once per change (`seedRevision`). Other settings you changed, such as its account, models or permissions, stay. A role you edited, even by one character, is left as it is; compare it with a new installation's profile or with the role texts in this guide if you want the new instructions. The update raises the profile's revision, like any edit.

## Build and start

1. Create a definition under **Pipelines → Definitions**. Add profile stages and arrange them in execution order.
2. Add verification or human approval after a stage when needed. A PR step is optional and authorizes publishing the run branch when that point is reached.
3. **Add parallel group** adds a stage whose members review the same changes at the same time, for example a security, a code and a UX reviewer (see [Parallel review groups](#parallel-review-groups)).
4. A review failure can return to an earlier stage with a finite repair budget from one through five iterations. **Continue the same session** on such a loop lets the stage it returns to resume its earlier CLI session instead of starting over (see below). The advanced graph editor preserves conditional routing that an ordered list cannot express.
5. Start a run with a task, an existing local Git repository and an optional base branch/ref. AgentPier creates a separate owned worktree and branch. It does not reset the original checkout or move its branch.

Each run freezes its definition and explicit profile settings. Later template edits affect future runs. Credentials remain in the existing account store and can be rotated; changing an account to an incompatible provider prevents subsequent turns from silently using another provider.

Open a run to see the current stage, attempt history, findings, usage and recovery actions. Every native turn has its own AgentPier session, with links to the familiar Chat and Terminal. Pipeline input is owned by the run; feedback is submitted through the pipeline action rather than typed into an active headless process.

## Outcomes and human decisions

The stage prompt specifies a private attempt-specific verdict path and the expected JSON structure: a `pass` or `fail` result, a summary, optional findings, artifacts and a `requiresHuman` flag. A stage that asks the owner may add `"question"` (the exact question, up to 2,000 characters) and `"files"` (up to 50 repository paths to look at); the run view and the inbox gate show both under **Question for you** and **Files to look at**. Every stage prompt names the run's base commit; a stage whose profile reads earlier verdicts also gets the newest verdict of each earlier stage (see [Risk gate](#risk-gate)). Completion requires the actual native turn outcome. An idle-looking terminal, an old verdict file or a successful-looking sentence is not sufficient.

Each stage attempt also gets a private report directory, `.pipeline/reports/<stage>/<attempt>/`, which the stage prompt names next to the verdict path. When a profile's role asks for a report, the agent writes it there (the built-in planner writes `PLAN.md`, the implementer `IMPLEMENTATION.md`, the code, security, UX and UI reviewers `REVIEW.md`, `SECURITY.md`, `UX-REVIEW.md` and `UI-REVIEW.md`, the app tester `TEST-REPORT.md` and the approver `APPROVAL.md`) and declares it as an artifact; code changes and files the task asks to change, including a tracked file with a report-like name, stay in the worktree. Checkpoints never commit `.pipeline/`, so reports stay out of the run branch and its pull request. A new attempt (loop-back, retry, the next round) gets a new directory; an operator-feedback or verification-repair turn of the same attempt writes into its own subdirectory, so a report declared by an earlier turn stays as it was. Each stage prompt lists the current reports of every stage: those of the stage's newest finished turn, so a later round without a report supersedes an earlier round's. AgentPier records the size and SHA-256 of each declared report when its turn finishes; reading a report that was rewritten afterwards marks it as `changed`, and the run view shows **Changed after the stage finished** above its content. A profile whose role text was edited keeps it after an update (see [Built-in profiles and pipelines after an update](#built-in-profiles-and-pipelines-after-an-update)); the stage prompt points report files that a role asks for into the report directory as well. A pipeline whose profile asks for a report at a repository path may therefore now find it in the report directory; a report that is still written and declared at a repository path stays readable, but it is committed like any other change.

A pass follows a pass edge, otherwise a default edge. A fail never follows a default edge. Verification, approval and PR effects apply only to the selected branch. On a bounded review loop, a failure containing only low-severity findings can advance; an explicit human-decision requirement always takes precedence. Missing or invalid verdicts get a bounded continuation opportunity, then require a human decision. Findings requiring a person and exhausted automatic repair loops remain visible at a gate.

Each pass over a loop edge is recorded as a round: its number, the stage that sent the run back (listed first), every stage that passed since the loop target last started (with its summary and notes), all their findings and the paths of their stage reports, plus the operator's note for a manual loop back. The run keeps the last ten rounds per loop edge, and a stage that a loop resets loses the loop context it had from an earlier round. The repair turn's prompt starts with the operator's note, passed in full as the operator's instruction. It then lists the current round's findings in full and the earlier rounds into the same stage compactly with the answers given then. This round data is marked as untrusted task evidence and kept within a fixed size: the oldest rounds go first, then the passing stages' notes, and the stage that sent the run back keeps at least one finding. Every finding of a round has an id such as `R2-1`; the number counts the rounds into the target stage, so rounds of two loop edges into the same stage never share an id. The repair turn answers them in a `responses` list of its verdict, `[{"finding":"R2-1","status":"fixed"}]`, where `not-fixed` and `disputed` need a `reason`. Ids are matched without regard to case, a leading `#` or dash variants, and a finding answered twice keeps its last answer. A malformed list is an invalid verdict. Answers to findings of earlier rounds, such as a confirmed earlier fix, are dropped silently; answers to ids no round has are dropped and named in the run history. A round whose repair leaves findings unanswered asks once, with one verdict nudge naming them, also when the repair is retried; the verdict is accepted afterwards. Turns that repair nothing may omit the list and are never checked against it. The stages of that round see the answers, and the findings that stayed unanswered, in their next turn. The run view shows the rounds as a timeline under the stage list (**Rounds**); a round opens to its findings with the repair turn's answer, **Answer pending** while the newest round's repair may still answer, or **Not answered**. Runs saved before this record only the failing stage's verdict for their pending repair turn and continue with it.

By default the stage a loop returns to starts over: a fresh kickoff in a new native session with the task, the round feedback and the latest stage reports. With **Continue the same session** turned on for the loop (`"continueSession": true` on the fail edge in the graph JSON; only a bounded fail edge accepts it), the repair turn resumes that stage's last native session (`codex exec resume`, `claude --resume`, `opencode run --session`) and keeps its earlier reasoning. Its prompt does not repeat the kickoff: it carries the round feedback described above, the paths of the current stage reports (reports can change between rounds) and this turn's verdict path and report directory. The resumed turn still opens a new attempt with its own report directory. A repair turn starts over instead, and records why, when the stage has no native session to resume, the session's context was reported as exhausted, or the stage's profile, account, provider connection, tool or model no longer match that session. When the resumed turn cannot start or fails (for example because the CLI no longer finds the conversation or reports an exhausted context), AgentPier keeps the CLI's error on that attempt and repeats the repair once as a fresh kickoff of the same round. Output that AgentPier could not validate stops for a decision instead. A usage limit or timeout parks the turn as for any other turn; resuming or retrying it starts over in a new session that still counts as the repair of its round (**New session (started again)**). The run's attempt history labels each repair turn **Same session** or **New session** with the reason for a fallback, shows the tokens each turn reported, and the **Rounds** timeline shows the session and the tokens of each round's repair, so resumed and fresh rounds can be compared.

Available actions depend on the current state: accept, approve risky changes (see [Risk gate](#risk-gate)), override, feedback, loop back, retry, reconcile a late verdict, wait for a usage reset, resume now, replace the spec (see [Spec and acceptance criteria](#spec-and-acceptance-criteria)) or abort. A run waiting for a decision also appears under **Gates** in the [inbox](inbox.md), where the same gate decision can be taken. The run retains previous attempts and decisions. Retrying PR creation retries that side effect instead of rerunning the agent's implementation stage.

**Override and continue** depends on what the stage is waiting on. A failed native turn (for example a session error or a timeout) continues with its result, but the stage's configured verification and human approval still follow. A stage parked at its gate because of a missing, invalid or failing verdict is approved by the override as that gate's decision; configured verification still runs if it has not passed. A stage whose verification failed is accepted as it is: the run advances without verifying again and without a separate approval. The confirmation names the path, and every override is recorded in the stage history and in the audit log with the stage, the overridden reason and the path. Reconciling is offered only while the turn's outcome can still succeed.

Some CLIs, notably `opencode run`, report their final step and then never exit. When a turn's native output reports completion and stays idle for a grace period, AgentPier stops the turn's process group and concludes the stage from that result. Every native turn is also bounded by an inactivity timeout and a wall-clock turn timeout that fail the stage clearly; a timed-out turn is stopped like a finished one, so it can still be retried or overridden. Operators can tune them in the data directory's `config.json`: `"pipelines": { "completionGraceSeconds": 30, "inactivityTimeoutMinutes": 120, "turnTimeoutMinutes": 360 }` (`0` disables the wall-clock bound).

## Parallel review groups

A parallel group is one stage with 2 to 8 members, each running its own profile. In the graph JSON it is a node `{"id":"review","kind":"parallel","members":[{"id":"security","profileId":"…"},{"id":"code","profileId":"…"}],"concurrency":2}`; member ids share the namespace of node ids, each member runs a profile of its own (the same profile twice would review the same changes the same way twice, so the graph and the editor refuse it), and edges name the group, never a member. The group has one set of pass, fail and default edges, so verification, approval, a pull request and a loop back follow it exactly as they follow a stage. A loop may return from a group to an earlier profile stage but never into a group. `concurrency` (from 1 to the number of members, **Members working at once** in the editor) caps how many members work at the same time; without it all start together.

Each member turn is a turn of its own: its own native session, verdict path, report directory, port block and browser session, and its own attempts in the history. Members get the task, the spec and the round context like any stage. In the next round each member sees the repair turn's answers to the findings it raised itself, and its unanswered findings; it gets only a count of the other members' findings, which they check themselves. A member whose verdict is missing or invalid gets the usual verdict nudges. When every member has reported, the group joins their verdicts: it fails when any member fails and requires a person when any member does. The rule that a review loop advances on low-severity findings only applies to each member on its own, so one member's low findings never turn another member's failure into a pass. The group's verdict lists every member's findings tagged with the member's profile, and a failing group sends the run back once, as one round with every member as a stage (failing members first). The risk gate checks the group once, when it concludes.

Members are read-only reviewers on the run's worktree. AgentPier commits what the worktree holds when the group starts and checks it once when the group joins; a member that changed or committed files stops the group at its gate (**A member of the group changed files**). A retry after a failed starting commit takes it then; a group that still has no starting commit when it joins stops at the same gate, because it cannot show that the members changed nothing. **Override and continue** there accepts the changes, which are committed with the group's checkpoint, and concludes with the joined verdict; **Return for repair** sends the run back.

A member that fails (a session error, a timeout, a missing verdict) does not stop its siblings. Once all members have settled, the group waits for a decision (**A member of the group needs a decision**). The run view shows the members side by side with a live verdict chip each, in the stage list and in the group's detail, and offers each blocked member its own actions: **Restart member**, **Check result again**, **Count as passed** (the member counts as passed without a valid result) and **Retry with feedback** when its session can continue. These decisions apply to the member's turn of the current round only: a member that could not start this round (for example without a free port block) offers only **Restart member**, and an earlier round's verdict never counts again. For the whole group, **Restart stage** starts every blocked member again and **Override and continue** overrides them all; its confirmation names the members that will count as passed without a review result, and members that already reported keep their verdicts. **Check result again** exists per member only: a group has no turn of its own to check. When the joined verdict asks for a person because a member requires one, the group waits at its gate with that member's question, and the member offers **Retry with feedback** in its own session; the group joins again once it answered. A usage limit parks the whole group with one reset time; waiting for the reset or **Resume now** starts only the members that hit it, and a member that waits for another decision keeps waiting. Verification after a group runs as for a stage, but a failure stops at the gate because a reviewing group cannot repair it. Member overrides are audited with the member's id, and a group override with the ids of the members it accepted (`members`) and the path `members-pass` (or `accepts-changes` for changed files).

## Spec and acceptance criteria

A stage can write a spec that becomes the run's contract. The built-in **Spec writer** profile (planning) inspects the repository and writes `spec.md` into its stage report directory with the sections `## Context` (real paths), `## Requirements`, `## Acceptance criteria`, `## Out of scope` and `## Assumptions`, and declares it in its verdict as an artifact with a role: `{"path":".pipeline/reports/<stage>/<attempt>/spec.md","role":"spec"}`. Any profile can do the same; the role is the only signal. AgentPier accepts a declared spec only from the declaring stage's report directory, up to 64 KiB, with at least one numbered item under `## Acceptance criteria`; otherwise the verdict counts as invalid and the stage gets the usual verdict nudge with the reason. Criteria are the top-level numbered items of the first heading that starts with "Acceptance criteria", numbered in order as `AC1`, `AC2` and so on; a `Verify:` part of an item says how to check it. Nested items and indented lines belong to the item above them, and an unindented paragraph after a blank line ends the list, so neither adds nor shifts a criterion. An assumption that starts with `[product decision]` is recorded with `productDecision: true`, so a later approver can ask the owner about it. The run stores the spec's text, its SHA-256, the criteria and the assumptions as `run.spec`.

Every later stage's prompt names the spec by path and lists its criteria, also in a resumed repair turn. Its verdict reports per criterion in `"criteria":[{"criterion":"AC1","status":"met" or "not-met","evidence":"…"}]`, and a finding may reference a criterion with `"criterion":"AC2"`; ids are matched without regard to case, a leading `#`, dashes or a missing `AC`, and an integer such as `2` counts as `AC2`. A malformed entry makes the verdict invalid; entries and references for ids the spec does not have are dropped and named in the history. A stage whose profile is in the implementation group must report every criterion: a verdict that leaves some out is asked for them once with a verdict nudge and accepted afterwards. Reviewers and other stages report the criteria they checked.

The spec stays a draft while its own stage runs, including feedback turns at its gate. Each of its turns is told where the current draft is and that a change counts only when the complete spec is written into that turn's report directory and declared again; a draft edited in place without a new declaration makes the verdict invalid and the stage is asked to declare it. The spec freezes when a turn of another stage starts. From then on, AgentPier checks the file after every turn, after every verification and before every new turn: a changed, deleted, linked or hard-linked file is restored to the recorded text without writing through a link. The run records each change with its source (the stage whose turn made it, **Verification**, or **Edited outside a turn**), the SHA-256 of what it found and whether the restore succeeded; a restore that fails is recorded as such (**Changed the spec; could not restore** in the attempt history), every later check tries again, and a failure that repeats the last one is not recorded twice. A later declaration of another spec is ignored and marked on its turn, and a spec stage that runs again after the freeze is told so.

Only a gate decision changes a frozen spec: at any stage waiting at its gate, **Replace spec** in the run view or the inbox lets the owner write a new text, which must again list acceptance criteria and may be up to 64 KiB. The owner's text is stored as a revision of its own at `.pipeline/spec/owner-<n>/spec.md`, which is never committed; the spec stage's report and earlier revisions stay unchanged. The run keeps each revision's number, source, path, size, SHA-256, stage and time, and **Revisions** in the run view opens each one with the text it has (flagged when its file changed since); the API serves it at `GET /api/pipeline-runs/<run>/spec/revisions/<n>`. An imported history-only run keeps only the current spec's text; earlier revisions answer that they are not available. The replacement is audited as `pipeline.updated` with the detail `kind: "spec"`, the stage, the revision number and its SHA-256, apart from the request's own audit entry. The gate keeps waiting for the decision. When the spec stage is asked again after a replacement, for example with **Retry with feedback**, its prompt names the owner's revision as the draft to start from. If a stage's declared spec was rejected and its verdict parked, its gate offers **Replace spec** too, so the owner can give the run a contract before overriding. The run view shows the spec at the top: whether it is a draft or frozen, who wrote it, its path, the criteria with their checks, the assumptions with product decisions marked, its revisions and any recorded change. **Show spec** opens the full text, and each stage lists its criteria report under **Acceptance criteria**.

For an "approve spec" step, add a human approval after the spec stage: the gate shows the spec, **Retry with feedback** lets the spec stage rewrite it, and **Replace spec** replaces it directly. An existing installation gets the **Spec writer** and **Approver** profiles with its next update (see [Built-in profiles and pipelines after an update](#built-in-profiles-and-pipelines-after-an-update)). Assumptions marked as product decisions are also listed in every later stage's prompt, and the [risk gate](#risk-gate) asks the owner to confirm each one once.

## Verification and evidence

Verification settings belong to a registered project under **Pipelines → Verification**. Commands are stored in AgentPier's data directory rather than taken from an agent-editable gate file in the repository. Configure each command's name, timeout and whether a failure blocks the stage. A configuration supports at most 20 steps with a combined timeout of two hours.

The exact plan is frozen for each gate attempt when used; edits can affect a later attempt but never rewrite an in-flight execution. Every step runs, even if an earlier one fails, and each has an individual timeout and a bounded tail of 8,192 log characters with an explicit truncation indicator. Blocking failures, missing execution and timeouts cannot become a successful verification result. Run details retain the plan, outcome and logs alongside stage diffs and declared artifacts.

Artifact reads are bounded and confined to the run's worktree and declared evidence. Within `.pipeline/`, only declared files inside a report directory of the stage's own attempts can be read; verdicts and other turn files stay private. Credential directories, dotenv files (`.env` and `.env.*` at any depth), PEM/key files, traversal and symlink escapes are rejected. Private filename checks ignore case. Checkpoints also exclude these private files when they were already staged; removing them from the index preserves their working-tree contents. Every accepted or overridden completed stage records a Git checkpoint. A diff identifies that recorded boundary; later repair attempts do not erase previous attempt records.

## Ports and browser sessions

Stages of parallel runs work on the same machine at the same time, so every native turn gets its own resources instead of the ports a repository's docs name. Its CLI process receives:

- `AGENTPIER_RUN_ID` and `AGENTPIER_STAGE_ID`: the run and the stage of the turn.
- `AGENTPIER_PORT` and `AGENTPIER_PORT_COUNT`: a block of consecutive ports leased to this turn, from `AGENTPIER_PORT` through `AGENTPIER_PORT + AGENTPIER_PORT_COUNT - 1` (currently three ports, for example `20110`–`20112`).
- `AGENTPIER_BROWSER_SESSION`: a browser session name for this run and stage, `agentpier-<run>-<stage>`, for tools with named sessions such as `agent-browser --session`.

The stage prompt states the same ports and session name and tells the agent to start every dev, preview, API or test server on them, and to stop its servers and browsers before it writes the verdict. Verification steps are run by AgentPier itself, not by a native turn, and get none of these variables.

The built-in **App Tester**, **Implementer**, **Security Reviewer**, **UX Reviewer** and **UI Reviewer** profiles use the variables when they are set and the repository's documented ports otherwise, for example when they are launched as a standalone session. **App Tester (interactive)** is unchanged. An app tester whose role text was edited keeps it after an update; add the port and session instructions to it yourself if needed.

A block is leased per active turn. Blocks start every ten ports in the range `20100`–`20999` by default, which stays clear of AgentPier's own port, the Vite dev server and the ephemeral ports of Linux and macOS. A different range can be set in the data directory's `config.json`: `"pipelines": { "portRangeStart": 30000, "portRangeEnd": 30999 }`. Both values lie between 1024 and 65535 and span at least ten ports; an invalid range keeps the default. Like the other `pipelines` settings, a change applies at the next server start. A block that contains AgentPier's own port is never leased.

The lease is stored with the run's active turn; a [parallel group](#parallel-review-groups) leases one block per member turn. It is released when the turn ends, fails, times out or is cancelled; a turn recovered after a restart keeps its block, and no block is leased twice. A stage takes its previous block again while that block is free. When leasing, AgentPier skips blocks with a port that is already in use on the host, probing IPv4 and IPv6 loopback and both wildcard addresses; a program that binds such a port later is not detected. When the range has no free block, the stage stops with a launch error that can be retried.

AgentPier itself reads `AGENTPIER_PORT` as its listening port, so a stage that starts AgentPier from its worktree listens on the leased port. AgentPier's Vite dev server still proxies to port 4380 and the dev origin allowlist expects port 5173, so such a stage tests a built AgentPier (`npm run build && npm start`) rather than `npm run dev`.

Dev servers a stage starts in the foreground or as background jobs of its shell belong to the turn's owned process group and stop with it when the turn ends, is stopped or the run is cancelled (see below). A process that detaches into its own process group or session (for example with `setsid`, a daemon mode or a service manager) is outside that guarantee and keeps its port until it exits; the next lease then skips that block. Browser tools that keep a background daemon per session may detach this way, which is why the prompt asks the agent to close its browser session itself.

## Risk gate

The risk gate stops a run for the owner when it changes risky paths or rests on a product decision, without relying on an agent's judgement. Risk rules belong to a registered project and sit under **Pipelines → Verification**, below its verification steps, in the **Risk rules** card: the **Risk gate** switch, path patterns (one per line) and the switch **New dependencies need approval**. Each card saves on its own (**Save verification steps**, **Save risk rules**). Like the verification steps, the rules are stored in AgentPier's data directory (`pipelines/definitions.json`), never in the repository; only the owner's settings route `PUT /api/pipeline-risk/<project>` changes them. No MCP tool, verdict, prompt or file in the run's worktree can read or change them. Every save is audited as `pipeline.updated` with the detail `kind: "risk-rules"`, whether the gate is on and the number of patterns.

**Default rules and existing installations.** A project without saved rules uses the default rules. This includes projects registered before risk rules existed, projects that a session or a pipeline registered on its own, and runs whose project cannot be identified; none of them runs without a check. After an update, runs of existing projects therefore stop for approval when they touch, for example, `package.json`, `.github/**` or a migration. The card says **Using the default rules** until the owner saves; **Use default rules** puts them back into the form. Turning the **Risk gate** switch off and saving disables the gate for that project, including the product-decision check; that saved decision is audited like any other rule change.

The defaults cover package manifests and lockfiles (`package.json`, `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `requirements*.txt`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `Gemfile`, `composer.json` and their lockfiles) and `.gitmodules`; CI, build, deploy and hosting files (`/.github/**`, `/.gitlab-ci.yml`, `/.circleci/**`, `Jenkinsfile`, `Dockerfile*`, `docker-compose*`, `Makefile`, `/scripts/**`, `/deploy/**`, `/infra/**`, `*.tf`, `vercel.json`, `netlify.toml`, `fly.toml`, `Procfile`); migrations and SQL (`migrations/**`, `*.sql`); and authentication, permissions, payments, storage rules and e-mail (`auth/**`, `permissions/**`, `payments/**`, `billing/**`, `*.rules`, `email/**`, `mail/**`). They also flag new dependencies. At most 100 patterns are kept.

`*` matches within one file or folder name and `?` matches one character. `**` as a whole path segment spans any number of folders; inside a name it acts like `*`. `{a,b}` lists alternatives. A pattern starting with `/` applies from the repository root; any other applies at every depth, so `auth/**` also covers `src/auth/token.js` and `package.json` covers every `package.json`. A pattern ending in `/` covers everything below. Matching ignores case and takes time proportional to the path and pattern lengths. A pattern may hold at most one `{…}` group of up to ten alternatives and at most ten wildcards.

A new dependency is an entry that a manifest declares after the change and did not declare at the run's base. The manifests read are:

- `package.json`: dependency sections, `overrides` and `resolutions`;
- `composer.json`: `require` and `require-dev`;
- `requirements*.txt`;
- `pyproject.toml`: PEP 621 dependencies and optional groups, Poetry tables;
- `Pipfile`;
- `go.mod`: `require` and `replace`;
- `Cargo.toml`: dependency tables, including dotted keys;
- `Gemfile`.

A version change of a registry dependency does not count. A dependency that now comes from another source does: git, a URL, a local path or file, an npm `github:` or `file:` specifier, a new `-r`/`-e` line or a `replace`. A submodule whose pointer moved counts too. A manifest that exists afterwards but cannot be read (unparseable or larger than 1 MiB) counts as an unknown new dependency. Lockfiles and other manifests are covered by the path patterns only, which stay the primary control.

**When the gate checks.** When a stage concludes, AgentPier lists every file the run changed between its base commit and the stage's checkpoint (`git diff --raw --find-renames`). A rename counts with its old and its new path, and a deleted file with its path. Only AgentPier's own run area (`.pipeline/`, `.agentpier-worktrees/`) is left out: a `.env` or key file an agent committed itself is checked, and a rename out of the run area counts as an added file. Assumptions of the run's spec marked `[product decision]` (see [Spec and acceptance criteria](#spec-and-acceptance-criteria)) are gate items as well, keyed by their text: a revised spec only asks again for a decision whose wording is new.

Any path, dependency, submodule commit or product decision the owner has not approved yet parks the stage at the risk gate (**Risky changes need your approval**). This happens before its verification, its human approval, a pull request or the next stage, also when every verdict passes. A failing stage that loops back for repair is not stopped; the gate follows the repair's conclusion. Before anything is pushed, AgentPier commits what the worktree holds and checks the run up to that commit again: when a stage's pull request is created or refreshed, when publishing is retried after `pr-failed`, after an override of failed verification, and for **Create / update pull request** on a completed run. A file that verification or a leftover process wrote after the stage's checkpoint is therefore checked too. A completed run with new risky changes is reopened at its last stage's risk gate. There the owner only decides on publishing: **Approve changes** publishes it, and **Don't publish** keeps the run completed without a pull request (audited with `decision: "decline"`); the finished stages are not reworked. The push sends exactly the checked commit (`<commit>:refs/heads/<branch>`), so a commit that lands while GitHub answers is never published. If the worktree changed before the push was prepared, publishing fails as `pr-failed`, and a retry checks again. If the commit before the push cannot be made (for example a stale Git lock or a failing hook), the stage parks as `pr-failed` with that reason instead of trying again on its own. The run view and the inbox gate list each item: the path with its rule, the other side of a rename, a new dependency, a submodule commit, or the product decision with its text.

**Approve changes** records the listed items on the run (`run.risk`) and continues where the gate stopped. A stage concludes as it would have: its verdict, verification and its own approval gate still apply, and an escalating verdict still asks the owner. A pull request is pushed, and a completed run is published. A later check stops again only for an item that was not approved yet. An approved path may therefore change again without a new stop, while a new dependency in an approved manifest stops the run. **Retry with feedback** sends the stage back instead, and **Stop run** ends the run.

The run view lists the owner's decisions per stage under **Risk gate decisions**. Each approval is audited as `pipeline.updated` with the detail `kind: "risk"`, the stage, the approved paths (at most 200) and the number of items. A gate lists at most 200 items; the rest are matched again after the approval. If the changed paths cannot be read, the stage parks at the risk gate with that reason, shown in the run view and the inbox; approving then continues without the check, for that exact commit only.

The built-in **Approver** profile (review group) is meant as the last stage before the owner. It reads the spec, the earlier stages' verdicts including the implementer's report per criterion, every review and test report and the run diff. It spot-checks at least one acceptance criterion itself, and either passes or sets `"requiresHuman": true` with the exact `question` for the owner and the `files` to look at. It escalates for authentication, payments, permissions, storage rules, deploy, CI, hosting or build scripts, migrations, e-mail, production data, new dependencies, product-decision assumptions, unmet criteria and open findings. Its profile has **Read earlier stages' verdicts** turned on (`"earlierVerdicts": true` in `config.run`): only a stage with this option gets the newest verdict of each earlier stage (result, summary, finding titles and the per-criterion report, as untrusted claims within 16 KiB) and the risky changes the owner already approved. Other stages, such as independent reviewers, review on their own. The risk gate does not depend on the Approver: it applies to every stage of every pipeline.

## Software factory

**Software factory** is a built-in pipeline that takes a task from a spec to a pull request with as few human steps as the run allows. Like every built-in item it is an editable starting point under **Pipelines → Definitions**:

```
Spec writer → (optional spec approval) → Implementer → Run verification
  → parallel review [Security, Code, UX, UI] → Approver → Create pull request
         └── on failure, back to the Implementer (2 rounds, same session)
```

1. **Spec writer** inspects the repository and writes `spec.md` with numbered acceptance criteria (see [Spec and acceptance criteria](#spec-and-acceptance-criteria)). The spec freezes when the implementer starts.
2. **Implementer** works against the spec, reports every criterion with its evidence and writes `IMPLEMENTATION.md` into its report directory. It starts servers and browsers on the turn's own ports and browser session (see [Ports and browser sessions](#ports-and-browser-sessions)).
3. **Run verification** runs the project's verification steps from **Pipelines → Verification** (see [Verification and evidence](#verification-and-evidence)). A blocking failure goes back to the implementer's session with the check output, at most twice; a third failure waits for the owner. A project without steps passes this step as not configured, so configure the steps you trust before relying on the factory.
4. A [parallel group](#parallel-review-groups) of four read-only reviewers looks at the same changes: **Security Reviewer** (`SECURITY.md`), **Code Reviewer** (`REVIEW.md`), **UX Reviewer** (`UX-REVIEW.md`: flows, empty, loading and error states, copy, accessibility, phone width and touch) and **UI Reviewer** (`UI-REVIEW.md`: consistency with the project's styling system, tokens and components, responsive layouts and themes). Each reviewer checks the spec's criteria and links a finding to the criterion it affects. A reviewer whose part does not apply, for example the UI reviewer on a backend change, passes and says so.
5. When a reviewer fails, the run goes back to the implementer as one round with every reviewer's findings, at most twice. **Continue the same session** is on, so the implementer resumes its earlier CLI session (see [Outcomes and human decisions](#outcomes-and-human-decisions)). Verification and all four reviewers run again after each repair.
6. **Approver** reads the spec, the earlier verdicts and every report, spot-checks a criterion and either passes or asks the owner (see [Risk gate](#risk-gate)).
7. **Create pull request** publishes the run branch and opens the pull request. The repository needs a remote; for a local repository, turn off **Create pull request** on the approver's stage.

The [risk gate](#risk-gate) is not a stage of the graph: it applies to every stage of every run. In the factory it typically stops the run after the implementer, before verification and review, when the change touches a risky path, adds a dependency or rests on a product decision of the spec; after **Approve changes** the run continues. It checks again before the pull request is pushed.

**Spec approval.** The spec gate is off in the built-in pipeline, so a run needs no human until something goes wrong. To review each spec before any code is written, open the pipeline under **Pipelines → Definitions**, edit stage 1 (**Spec writer**) and turn on **Human approval**. The gate then shows the spec, and the owner can approve it, ask for a rewrite with **Retry with feedback** or use **Replace spec**.

**What still needs a human.** The factory never merges. A person:

- assigns accounts and models to its profiles (the built-in profiles use the local Claude account), configures the project's verification steps and checks its risk rules;
- decides at the risk gate on risky paths, new dependencies and product decisions;
- answers the approver when it escalates (security-sensitive areas, deploy, CI or build scripts, migrations, unmet criteria, open findings) and the spec gate when it is on;
- decides when the review loop is used up after two rounds, when verification keeps failing, when the approver fails, and when a stage or reviewer cannot produce a valid result;
- reviews and merges the pull request; downstream CI is not awaited.

**Models per role.** The built-in profiles leave the model empty, so each stage uses its account's default model until you choose one in the profile. The factory works best with a strong model for the stages whose mistakes are expensive and a cheaper, faster one for the narrower reviews:

| Stage                                                 | Suggested model                             |
| ----------------------------------------------------- | ------------------------------------------- |
| Spec writer, Implementer, Security Reviewer, Approver | the account's strongest model               |
| Code Reviewer, UX Reviewer, UI Reviewer               | a cheaper, faster model of the same account |

Set the model under **Pipelines → Profiles** in each profile's model selection. The suggestion is not enforced; an account or provider that offers only one model keeps that model for every stage.

## Restart, cancellation and cleanup

Run state, attempt identity and native session identity are durable. A web-only restart reconciles the existing turn instead of launching another copy; a run records one active turn per stage (`activeTurns`), so every running member of a parallel group is reconciled on its own. Runs saved by earlier versions with a single `activeTurn` are read in the new shape. Aborting stops every member's turn. Downgrading to a version before parallel groups while runs are active is not supported: such a version does not see the active turns this version records, so it can neither stop nor reconcile them, its abort leaves the CLIs running, and their ports may be leased again. Finish or abort running runs before a downgrade. When such a run comes back to this version, only the turn the earlier version recorded counts as active. Interrupted or ambiguous side effects become an actionable state; they are not silently reported as completed.

Aborting stops the pipeline's owned process groups and preserves the worktree. Native workers and verification commands start only after a second process in the same group is ready to watch their keeper. Losing either the keeper or its watchdog terminates the owned group, including descendants that ignore SIGTERM. Group termination is not an operating-system sandbox: a program that deliberately detaches into a separate process group is outside that guarantee. Deleting a finished run is the separate cleanup action. Cleanup checks ownership and refuses active native processes and uncommitted changes. Commits that exist only locally (for example in a repository without a remote) need an explicit confirmation; the run branch keeps them after the worktree is removed. Pull requests are offered only for completed runs in repositories with a remote, and a pipeline with a pull request step cannot start in a repository without one. The source checkout and unrelated directories are outside the removal operation.

An optional PR action uses the existing host-scoped GitHub credentials and GitHub CLI. It publishes the run's branch and opens or refreshes its PR; later completed stages refresh the branch and summary of that existing PR. It does not merge the PR or wait for downstream CI. No push or PR is performed merely because a run finishes without a PR step.

PR publication accepts `main`, `origin/main`, `refs/remotes/origin/main`, or `refs/heads/main` as the base and sends GitHub the branch name `main`. Nested branch names are preserved. On `pr-failed`, Retry repeats publication without rerunning implementation or review. It discovers an existing open PR by its head branch, including drafts, and updates that PR instead of creating another. A manually created PR does not clear the recorded pipeline error until Retry succeeds.

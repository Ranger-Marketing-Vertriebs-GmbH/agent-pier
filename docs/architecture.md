# Architecture

AgentPier hosts native coding CLI sessions on one macOS or Linux machine. React is the browser client; an Express application owns configuration, domain services and a private tmux server. The browser never runs a separate model conversation. Chat sends input to the same session displayed in Terminal.

## Boundaries

| Directory            | Responsibility                                                                     |
| -------------------- | ---------------------------------------------------------------------------------- |
| `web/app`            | Application shell, URL navigation, workspace state and top-level dialogs           |
| `web/features`       | User-facing feature components, state hooks and local styles                       |
| `web/components`     | Shared controls, dialogs, pagination and error presentation                        |
| `web/lib`            | HTTP client, asynchronous action handling, provider labels and locale dictionaries |
| `web/styles`         | Global primitives, application layout and viewport rules                           |
| `server/application` | Service construction, session launch orchestration and shutdown                    |
| `server/http`        | Express routes, the API registry and route access, WebSocket transport             |
| `server/features`    | Domain services and native CLI adapters, grouped by capability                     |
| `server/lib`         | Filesystem/configuration boundaries, serialization, shared errors and locale data  |
| `tests`              | Unit, integration, blackbox, property, matrix and browser suites                   |

Keep business rules in their feature service. HTTP handlers validate transport shape, call the service and serialize public results. Components render feature state; shared components must not acquire dependencies on feature services. `npm run check:structure` rejects first-party source, style and test files above 600 lines. Extract by responsibility before reaching that limit; splitting one large class across arbitrary numbered files does not establish a useful boundary.

First-party identifiers and comments are English. German product text lives in explicit locale dictionaries. Native protocol names, recorded CLI text and parser examples retain their original spelling.

Each coding CLI (Codex, Claude Code, OpenCode) is described in `server/features/clis/`: a browser-safe definition record that the web app also imports, and a Node-only driver for profiles, launch additions, provider launches, MCP entries, native session binding, approval relay, history, terminal reading, pipelines, plugins and profile files. Features ask the catalog and the drivers instead of branching on the CLI id; `tests/unit/cli-id-lists.test.js` keeps the remaining branches from growing. See [coding CLIs](coding-clis.md).

## Session launch and lifetime

The launch orchestrator validates the account, directory and launch mode, then composes host-bound GitHub credentials, AgentBus, repository memory, project SSH and native history binding. Each adapter returns additions to a launch description. Failed launches unwind generated resources. Account/provider changes are rejected while affected sessions run. Account usage is also reserved during launch preparation and reloads, including both accounts during an account switch; failed or deferred attempts release their reservations.

`SessionManager` serializes session operations, owns the private tmux socket and persists public session metadata. A web-process restart reconnects to existing terminals; it does not terminate them. Sessions are named `agentpier-<id>` and run on one tmux server per data directory, on `/tmp/agentpier-<uid>-<hash>/tmux.sock` (`server/features/sessions/tmux-naming.js`). Sessions and servers of releases before 2.6, which carried the former product name, are not read: AgentPier neither lists nor ends them. Release manifests list the session name forms a release understands in `tmuxNames`; activation and rollback refuse a release whose manifest lacks `agentpier`, and the release list shows it as not rollbackable (`server/features/operations/release-schema.js`).

The stable `server/terminal-launcher.js`, `server/adapter-process.js`, `server/git-credential.mjs`, `server/github-credentials.js`, `server/native-session-binding.js` and `server/native-session-opencode.js` entry points are referenced by persisted or running CLI configurations. They remain compatibility boundaries even when their implementations move into features.

## Chat and native observations

Native history adapters normalize stored messages, tasks and available telemetry. Claude Code moves a session transcript into the project directory of its current working directory when it enters or leaves a worktree; the history adapter therefore resolves a transcript by session id across every project directory of the profile and readers verify the transcript's own cwd and session id before use. The chat store maintains a bounded snapshot and its explicit provenance. Native-bound sessions expose their authoritative conversation without a manual conversation picker; the backend rejects manual rebinding. Legacy sessions without native binding retain manual selection. A missing field remains unknown; configured model metadata must not be presented as a native observation. Session activity (working, ready, waiting) comes first from the CLI's own reports. Claude Code sessions carry an `agentpier-activity` plugin whose asynchronous `Stop`, `StopFailure`, `PermissionRequest`, `PreToolUse[AskUserQuestion]`, `Elicitation` and `SessionEnd` hooks, together with the identity plugin's `SessionStart` and `UserPromptSubmit`, write `native-sessions/<id>.activity.json` for the current launch token; `Stop` with running `background_tasks` counts as working. The Codex request bridge derives the state from the app-server's `turn/started`, `turn/completed` and `thread/status/changed` notifications, and the OpenCode TUI plugin from the visible session's busy status and pending dialogs. A pending AgentPier approval or question always means waiting. The terminal reader stays the fallback for older sessions and shells, and corrects a report it contradicts: Claude Code sends no event on Esc or a crash, so a reported turn or wait ends as soon as the session's transcript shows Claude's `[Request interrupted by user]` marker as its newest row after the report (recorded as an `Interrupt` report), or when the terminal shows an idle composer that has not changed for 15 seconds, and any report without screen changes for 10 minutes falls back to the terminal reading. An ended report stays ended until the CLI reports again, so typing in the terminal after Esc cannot revive it. A reload's last check under the session lock uses the same combined reading. The terminal reader uses the current native composer area and bounded caching. Neither path sends model requests to discover activity. A Claude Code 2.1.287 or newer also loads AgentPier's `agentpier-bridge` mod; once it reports for a launch, its turn start and end (an interrupt included) decide working and ready instead of the terminal reading and the interrupt marker, and only a dialog the hooks report afterwards or running background tasks override it (`server/features/claude-mod/`). The same reports also reach an open chat directly over the session's authenticated native request channel, so it reads again without waiting for the file watcher, and a reply streams into the chat while it is written (Codex app-server deltas, OpenCode part events, Claude Code's `agentpier-bridge` mod token by token, or else its asynchronous `MessageDisplay` hook in its own `agentpier-stream` plugin line by line); see [live chat updates](native-chat-delivery.md#live-chat-updates). Live chat file observation follows the reader's scoped source paths, shares session-metadata directory watches and keeps healthy file and tmux observers across recovery reads. A bounded stat probe repairs replaced or missing files; broad account-profile watches are not used.

The URL owns durable navigation state: page, session, Chat/Terminal mode, extension/plugin profile, AgentBus selection and memory filters. Local component state owns transient drafts and pending operations. Navigation cancels obsolete reads; pending mutations retain their operation identity and cannot submit twice.

See [native observation semantics and limitations](chat-observability.md) for the per-CLI context formula, identity correlation and source ordering.

## Chat delivery confirmation

A chat message is pasted into the CLI's TUI and followed by Enter; the receipt (`server/features/chat/chat-delivery.js`) is then `handed-off`. Whether the CLI took the message is decided by the CLI's own submit event on the server, not by comparing text in the browser. The server sets the result through the normal receipt write, so `session.deliveries:<id>` pushes it.

- **Acceptance sources.** Claude Code with the bridge mod: the mod wraps `prompt.submit`, awaits `next(e)` and reports `prompt.accepted` (image file names, `queued`) or `prompt.dropped` (the hook's reason) as mod events. Codex: the app-server proxy pairs each `turn/start` / `turn/steer` `clientUserMessageId` with the `item/started` `userMessage` of the same id (`accepted`) or a start that a blocking hook ended without one (`dropped`) and pushes them as `prompt` and `prompt-ready` over the native channel (`server/features/requests/codex-prompt-acceptance.js`). Neither alters or delays the prompt. See [native chat delivery](native-chat-delivery.md).
- **Matcher.** `DeliveryAcceptance` (`server/features/chat/delivery-acceptance.js`) registers an expectation right before Enter (the moment, the uploaded image names). An event fits an expectation registered before the event's time whose image count equals the attachments sent and, for Claude, whose image file names match; it goes to the newest fitting expectation, and the older expectations still open are retired without a match (they had no event of their own, such as a hook-blocked steer or a command without a submit event, and their receipts end in the ask state instead of taking a later delivery's event). An event that fits two or more expectations registered within the ask window before it (`ASK_WINDOW_MS`, 8 s) is ambiguous: it confirms none of them and retires them, so their receipts ask; this applies to drops as well. There is no text comparison. An event that fits no open expectation is the owner's own prompt typed in the TUI and is ignored. An event that arrives before its expectation is buffered for 5 s, so a fast CLI is not lost. Expectations live for 10 minutes, at most 32 per session; an expectation is withdrawn when Enter is refused, deferred or never reached, and a retry replaces the earlier one of the same delivery. Events are dated with the server's receive time. A match is not tied to the session input lock, which the delivery releases shortly after Enter. A late event still turns a `handed-off` or `uncertain` receipt into `accepted`; the timeout only changes the wording.
- **Statuses.** `accepted` is terminal and counts as delivered, also for a message in the CLI's own queue. The receipt records how it is confirmed (`confirmation`: `events`, `screen` or `text`), when Enter was sent (`submittedAt`) and `acceptedAt`. The browser hides the notice on `accepted`.
- **Ask state.** A handed-off receipt without a result changes after 8 s into a question that offers checking the handoff and resending. The timer runs in the browser from its own handoff time (`web/features/chat/delivery-confirmation.js`, `useDeliveryClock`), not on the server, and a later acceptance still confirms. Handed-off receipts are re-read on live changes only until a minute after the ask.
- **Hook block.** On `dropped` the receipt becomes `rejected` with `CHAT_HOOK_BLOCKED`. Claude puts a blocked prompt back into its input box, so AgentPier clears the box (under the session input lock, with the draft keys, never Escape or Ctrl-C) only when a screen check proves it holds exactly the delivered text, including one chip per image path, and reads an empty box again after one settle. The text and attachments return to the composer (`released`). Anything else stays untouched and the receipt reads `CHAT_HOOK_BLOCKED_DRAFT`: the notice says the text is still in the CLI and resend is offered only once the box is empty, so a resend never doubles a prompt. Dismissing such a message also clears its unchanged copy in the composer.
- **Commands.** Text starting with `!` and the per-CLI local commands (`server/features/chat/delivery-commands.js`) send no submit event. They are confirmed from the screen after Enter (empty prompt box, no dialog or menu) and show "Command handed over" briefly. The screen never confirms an ordinary message.
- **Other consumers.** `ChatDelivery.settled(id, deliveryId, {timeoutMs})` waits (woken by receipt writes, 8 s by default) until a receipt leaves `pending`, `handed-off` and `uncertain`. Tickets, sequence starts and fixes (`ticket-service.js`, `sequence-start.js`, `sequence-fixes.js`) and agent steering (`session-steering.js`) await it through `confirmedDelivery` (`chat-delivery-blocked.js`): `accepted` is success (an unconfirmed `handed-off` stays success for sessions without a source), a hook block fails, and audit records it as `hook-blocked`.
- **Fallback.** Sessions without an acceptance source (Claude Code without the mod, Codex without the proxy, OpenCode) keep the text matcher of the browser (`native-delivery-state.js`) and the `handed-off` wording.
- **Dialog safety.** Delivery never types into a native approval dialog: dialogs and menus hold it first (`tests/integration/chat-delivery-dialog-safety.test.js`).

Known limitations:

- A native source becomes ready only after the mod or the proxy has reported, so the first delivery after a launch may use the text fallback. A Claude Code session launched before an update runs an older copy of the mod without prompt reports (its body lacks `prompts: true`) and keeps the text fallback until it is relaunched.
- A drop reason in a non-settings-hook format may carry prompt text, up to 500 characters.
- Acceptance events are dated with the server's receive time, not the CLI's clock.
- A prompt the owner types in the TUI at the very moment of a delivery cannot be told apart by id; the newest fitting delivery takes the event.
- Two deliveries sent within the ask window (8 s, `ASK_WINDOW_MS`) whose events cannot be told apart both end in the ask state: an event that fits both confirms neither, and no later event confirms them.
- A delivery's own event that arrives more than the ask window after its Enter may confirm the next delivery instead (by design): a delivery retired as ambiguous keeps an event ambiguous only until the ask window after its Enter ends.
- A sequence start that a hook blocks parks as "The task did not reach the session."
- A command that opens a dialog or panel (for example `/model` without arguments, `/config` or `/help`) ends in the ask state by design: the screen confirms a command only from an empty prompt box without a dialog or menu.

## File Explorer

`server/application/files.js` composes the Explorer services in
`server/features/files/`. The HTTP adapters expose the same service through a global
scope and a session-project scope. A scope ID is an opaque observation of the current
root and read-only state; every mutation must present that current ID. Session scope is
recomputed from canonical CWD and cannot be widened by a request. Headless pipeline
sessions are read-only. The global scope begins at the configured home but is bounded by
the host root and the server process user's OS permissions.

Listings use bounded snapshots. Jobs, publications, Trash adoption, uploads, and ZIP
artifacts are durable in private Explorer storage, allowing recovery after web-process
restart without guessing an unrecorded filesystem outcome. Recovery combines recorded
checkpoints with fresh path observations; it does not make external native writers or
final check/action races transactional. Native descriptors and platform probes preserve
metadata and prove supported name policies before strict writes.

The React Explorer owns navigation and scoped clients. `FileEditorContext` owns tabs and
attempted bytes across route changes in one browser runtime; it never persists draft
content. A context change clears current authority before its replacement read completes,
so retained tabs cannot write through a stale project scope. See the
[File Explorer guide](file-explorer.md) for user workflows, limits, platform constraints,
and HTTP route families.

## Project memory

Memory resolves Git worktrees to their common repository identity. Independent clones, submodules and unrelated directories remain separate. A private SQLite WAL database stores entries, immutable revisions and session capabilities. Updates require the expected revision, so concurrent writers receive a conflict instead of silently overwriting one another.

Every supported coding CLI receives a native MCP server bound to its AgentPier session and project. The server supplies writer provenance, validates capability on each call and exposes bounded search with explicit full-entry retrieval. Shell and login sessions receive no project-memory integration. Memory is deliberately stored as reference material; the application does not promote retrieved notes into trusted system instructions. See [memory contracts and tools](memory.md).

## Provider configuration

The provider catalog retains native identifiers, advertised context, routed context, output limits, source and freshness. Launch adapters separately translate account configuration for Codex, Claude Code and OpenCode. Public account/session projections omit credentials; provider keys are passed through isolated native environment/configuration mechanisms. A model label is not evidence of protocol compatibility or a successful connection. See [provider compatibility and limits](providers.md).

Custom endpoint connections add two features that let every CLI use any endpoint protocol; see [the protocol adapter](protocol-adapter.md). `server/features/protocol-adapter/` is the pure translation library between Anthropic Messages, OpenAI Responses and Chat Completions (no network or filesystem). `server/features/adapter-runtime/` runs it per session: the supervisor inside the terminal launcher, the adapter child process, the HTTP server and the diagnostics file.

## Native pipelines

Pipeline definitions and task profiles are independent from credential accounts. The definition store validates profile configuration and bounded graphs before atomically persisting revisions. Run snapshots retain explicit profile and public account configuration without secrets. The execution engine owns durable attempts, human decisions, bounded loops, verification and recovery; injectable native/workspace ports own process and Git effects.

Native stages reuse the session lifecycle's account, provider, GitHub, AgentBus, memory and history preparation through trusted internal launch options. HTTP request bodies cannot supply executable transforms or pipeline ownership. Headless turns remain normal observable sessions, while the engine owns their input. Exact native results and scoped verdicts drive transitions; terminal appearance does not determine success.

An owned worktree isolates each run from its source checkout. Cancellation preserves it, and deletion has a separate ownership check. Verification plans reside in application data and execute through private supervisors with bounded logs and receipts that survive a web restart. Pipeline routes, filters, profiles and evidence tabs use durable URLs. See [pipelines](pipelines.md) and the [implementation contract](refactor/pipelines-plan.md).

## Live channel

The browser follows changing server state over one WebSocket per tab, `GET /api/live` (`server/http/live-websocket.js`), instead of polling REST routes. The upgrade passes the same origin check, login and admission as the chat stream; logout closes the socket with 1008. At most 16 sockets are open per principal (more are refused with 429).

- **Hub.** `LiveHub` (`server/features/live/live-hub.js`) is a registry of topics. A topic id is a name or `name:param`. Subscribers of the same topic id and access scope share one topic instance (`live-instance.js`), which reads the topic once for all of them, coalesces change signals (150 ms debounce, at most 1 s), raises its revision only when the digest of the value changed, and runs its samplers and change sources only while someone subscribes. A topic the principal may not see answers exactly like an unknown one (`unknown-topic`). `server/application/live-wiring.js` defines the topics and the deny-by-default gate: the owner reaches every topic whose own `authorize` admits him, a restricted user only the patterns in `userTopics` (`server/http/route-access.js`): the `me.*` topics, each listed as the `topic` of the `/me` route whose answer it carries.
- **Topics.** `state` (the workspace state of `GET /api/state`, as rows; sessions, accounts, connections and preferences push on every write or collect, the slow CLI and utility detection is cached for 60 s), `session.requests:<id>` (the request list of `GET /api/sessions/:id/requests`), `session.models:<id>` (the model control of `GET /api/sessions/:id/models`), `inbox` (the owner inbox of `GET /api/inbox`), `agent.list` (the owner's agent list for the sidebar, the agents page and the settings, as rows: the `GET /api/assistants` body plus `runtime`, the `GET /api/assistant-runtime` answer, `server/features/assistants/live-topics.js`; it is read again on every `change` and `runtime` event of the agent services, binds to the new services when agents are switched on or off and reads again, and without agent services refuses with the routes' 404 or 503, marked as expected; its REST fallback reads both routes, the registry's `sections`; it replaced the `/api/assistant-events` server-sent event stream), the agent detail topics `agent.actions:<id>` (`GET /api/assistants/:id/actions`), `agent.coding-requests:<id>` (that list's team coding requests, those with a `teamId`), `agent.channels:<id>` (the agent's channels of `GET /api/assistant-channels`), `agent.reminders:<id>` (`GET /api/assistants/:id/reminders`), `agent.pinboard:<id>` (`GET /api/assistants/:id/pinboard`, the agent's pinned lists; pushed by every pinboard write and `seen` through `agentPinboardChanged`, and sampled every 30 s while a visible tab watches, because a pinned file can change without a tool call; owner only, `content: true` like the reminders), `agent.memory:<id>` (`GET /api/assistants/:id/memory/files`, the memory view's first page, with a Hermes agent's dream diary; pushed by every recorded Hermes night through `agentMemoryChanged`; owner only, `content: true`, so a user's own agent is refused without her opt-in, and the client falls back to a 30 s poll), `agent.senders:<id>` (`GET /api/assistant-telegram-senders/:id`) and `agent.ssh-agent:<id>` (`GET /api/assistants/:id/ssh-agent`, the agent's plain ssh status, pushed by every change of its SSH agent through `agentSshChanged` and by every agent change; it carries state, reason, aliases and an optional `sshConfig` code, never a path or token) and `agent.allowlist:<id>` (`GET /api/assistants/:id/shell-allowlist`, the always allowed commands: OpenClaw's allowlist and the exact commands AgentPier remembers, a Hermes agent's remembered commands alone; read again on every agent change and runtime event, because a decision, a remembered command answered and a deletion each end with one), which replaced the polls of the agent chat, settings and team cards (owner only, same file). They check privacy as their routes do: the actions, coding requests and reminders of a user's own agent are refused like an unknown topic without her opt-in (the owner-content guard's `agent` rule), and an opt-in that ends sends `revoked`, since every privacy and agent change checks every subscription again; the channel list is never refused but hides her Telegram identity and texts without the opt-in (`OwnerPrivacy#filterChannels`); the sender bots have no privacy check, like their route. These four, and `agent.list` (her chats show only under her opt-in, `OwnerPrivacy#view`), are the privacy-scoped topics: every topic whose read goes through owner privacy is marked `privacy: true`, and all of them start over on every owner-privacy change, synchronously and before any other frame (`LiveHub#resetWhere`, wired in `live-wiring.js`): each instance forgets its value, its subscribers' frames still held back by a slow socket are discarded, a read begun before the change is dropped, and it reads again at once and answers every subscriber with a fresh snapshot; a subscriber that joins meanwhile waits for that read, and a record without an instance forgets its digest, so a resubscribe never hears `same`. Their change sources: `AssistantWorkflows` reports every action write (`onChange`, once per batch, for the action's agent and its lead) and a pipeline run's save or deletion signals the agents whose actions started it (`agentRunChanged` in `server/application/pipelines.js`); `ChannelStore`, `ChannelLedger` and `ChannelOutbox` report every write the channel list shows (`onWrite`, not the poll offset), as do the team notification failures, through `ChannelService#onChange`, which also signals the reminders (a reminder's Telegram delivery state is an outbox entry), only of the written channel's agent when it is known (every agent's after a deletion or a batch write); the reminder service's writes (create, update, remove, review, disable) signal their agent's `agent.reminders` once they have settled, after the Gateway's cron job changed too, and every run result all of them (`followReminderWrites`, wired around `NativeReminders` in `server/application/assistants.js`); so do the bindings a user's release ends or forgets (a user who leaves, a member removed, a shared agent handed to her, `user-release.js`), except their retry at a Gateway start, which the sample picks up; the sender bots follow the agent services' `change` and `runtime` events, which every bot save ends with. The cron jobs and the bot's state live in the Gateway, which announces nothing (an agent's own cron tool, a next run moving on), so `agent.reminders` is also sampled every 30 s and `agent.senders` every 5 s while a visible tab watches. A failing hook is logged and the write stands. Without agent services or for an unknown agent they refuse with the routes' status, marked as expected. `pipeline.run:<id>` (a run of `GET /api/pipeline-runs/:id`; a run that does not exist or was deleted is `{ run: null }`), `pipeline.queue:<projectId>` (a project's run queue of `GET /api/pipeline-queue/:projectId`), `pipeline.counts` and `pipeline.counts:<projectId>` (the count of each run status and the total, of all runs or of one project, as `GET /api/pipeline-run-counts[?projectId=]` answers it), `pipeline.runs:<projectId|*>:<status|*>` (page 1 of `GET /api/pipeline-runs?view=list` with those filters, `*` for none: each run in its slim list view, without the execution log, verdicts, prompts or actions) and the signal `pipeline.runs.changed[:<projectId>]` (a `changed` frame on any run change, of that project, after which a later page of the run list reads its route once). The pipeline topics are owner only and push on every saved run, on a deleted run and on every queue change; a run's change also reaches the queue that started it, and only the counts and lists the run is or was listed in (`server/features/pipelines/live-topics.js`). A save that changes nothing of the run's list view (an execution log entry) wakes no list, and one that keeps its project and status changes no count. The counts come from an in-memory index (`run-counts.js`) built with one scan of the run store at start and kept current by every save and delete, so the status pills, the run tab's total and the project hints no longer list the runs. The run list pages in SQLite (`RunStore.page`): only the 20 listed documents are parsed. The menu hints and the start page follow `pipeline.counts`, page 1 of `awaiting-human`, `failed` and `running`, and three owner-only topics: `settings.summary` (`GET /api/settings/summary`), `connections.problems` (`GET /api/connections/problems`) and, with agents on, `runtime.updates` (`GET /api/assistant-runtime/updates`). Their sources (about ten stores, the cached release check and the network config) announce no change of their own, so their change source is the write middleware `liveWriteSignals` (`server/application/live-wiring.js`): every successful `/api` write except the frequent session, chat, agent chat, `/me`, file, run, memory and artifact writes signals all three once it has answered, until those stores announce their changes themselves. Switching agents on or off signals the last two, and `RuntimeUpdates` reports every phase, busy change and snapshot progress of an update (`onChange`), so the agent settings' update panel follows `runtime.updates` instead of polling every 2 s. An operations job that ends after its request answered (a backup) signals `settings.summary` at its end; an MCP grant that expires is not pushed until the next write. Live, only its `operations.updates` part is read. `connections.problems` and `runtime.updates` are also sampled every 60 s while a visible tab watches, for stored tests, installs and update phases that change without a write. All three read local state only: no connection test, token check or remote update check runs. Without agent services `runtime.updates` refuses with the route's status (404 with agents off, 503 when they do not run), marked as expected so the hub does not log it, and the client reads the route once. The operations topics are owner only (`server/features/operations/live-topics.js`): `job.operation:<id>` (an operations job, backup, restore, release stage, cleanup, migration, activation or rollback, as `GET /api/operations/jobs/:id` answers it) pushes on every status write of `OperationJobs`; a release activation or rollback is written by a helper process, so a watched job's file is also followed (fs.watch) and, while the job runs, sampled every 1.5 s; an unknown job is the route's 404, which is not logged. Every background job topic is a kind of the owner-only `job.<kind>:<id>` family, registered with `defineJobTopic` (`server/features/live/job-topics.js`): the job's source signals each status write, and a kind whose job something outside the server process also writes is sampled while its last read was `running`, never once it ended. Besides `job.operation` there are the tool kinds (`server/features/tools/live-topics.js`): `job.tool:<tool>` (one tool's installation and the installer's `busy`, as `GET /api/tool-installations?tool=<tool>` answers it; an unknown tool is the route's 404; `job.tool:chromium` is the managed agent browser, which the agent browser settings also follow while their install runs) pushes on every job write of `ToolInstaller` (start, each progress step, end, removal) and when the installer is no longer busy, so another tool's topic hears `busy` too; a list read while a CLI's version is still probed (`versionStatus: "checking"`) is pushed again once the version is known. It is not sampled. `job.rea:current` (`GET /api/rea`) pushes the start, each step and the end of a REA job (`ReaTool` onChange); its `jobCount` rises with every job, so a job that ends in the state it began with (a retry failing the same way, an apply that changes nothing) is still pushed. While a job runs it is also sampled every second, because Core's package install changes the state without telling REA. Without the MCP server store it refuses with the route's 503, marked as expected. `job.craft-anything:current` (`GET /api/craft-anything`, owner only) does the same for the managed Craft Anything tool (`CraftTool` onChange): the start, each step and the end of a job are pushed, and while a job runs it is sampled every second; without the MCP server store it refuses with the route's 503 as well. - **Frames.** The server opens with `{type: "hello", instance}`. The client sends `sub` (with `have`, the revision or row cursor it already holds), `unsub`, `ping` and `presence`. The answer to a `sub` is `same`, a `snapshot`, or for row topics a `delta` onto the client's cursor; later changes arrive as `state` (whole value) or `delta` (rows). Every `snapshot`, `state` and `delta` carries `readAt`, when the server began the read behind it, and every REST `GET` under `/api` answers with the same clock in `X-Read-Started` and the server instance in `X-Read-Instance` (`server/lib/read-stamp.js`; a write's answer carries the moment it is sent, after its handler read what it answers; stamps compare only within one instance, so after a restart neither a push nor a fallback poll is dropped): a read that answers from data read earlier (the session list of the last collect, a shared reminder sample) is dated to that data (`basedOn`); `useLiveTopic` shows whichever of a push and a REST answer was read later, so a push read before a write never undoes the `refresh()` answer that already shows it. `stale` asks the client for one REST read (a value over the topic's byte limit), as does an `error` without code when a read of the topic failed (once per subscriber until a read succeeds again, which is then pushed even if it equals the last value; a later failure, such as the queue of a project that was removed, also reaches subscribers that hold a value: their tab keeps it beside the route's error for a passing failure, and drops it when the route refuses it for good (404, 403); a subscriber that joins an instance whose last read failed makes it read again and is answered by that read, never by the stored value, and the first read that succeeds answers every waiting subscriber; in the tab, a listener that joins a topic whose read failed while no value is held gets that failure too and reads the route itself, as it gets a `stale` or a refusal, instead of waiting for a push that comes only after a successful read); `revoked` ends a subscription whose access was withdrawn (the browser drops the value it showed at once, discards a read under way and reads nothing over REST; it subscribes the topic again every 30 s while the tab is visible, and on the next connection, so access that comes back recovers in place, while a topic still refused stays revoked), and `changed` is a signal without data.
- **Views topic.** `views` is an owner-only state topic: the whole saved-views document of `GET /api/views` (`dataDir/views.json`, written by `ViewStore` in `server/features/views/`), signalled by every successful `ViewStore` write (`server/features/views/live-topics.js`). Every read and write answer, and so every frame, carries a random per-instance `epoch` (new on each server start, so also after a restore); a browser adopts a document of another epoch even if its version is lower, so a restored or restarted store never leaves the sidebar on stale layouts. `/api/views` is a quiet write area: a write does not signal the generic workspace topics, only `views`. See [Views](views.md).
- **Review comment topics.** `session.review:<sessionId>` and `pipeline.review:<runId>` are owner-only state topics (`server/features/changes/live-topics.js`) whose value is the answer of `GET /api/sessions/:id/review-comments` and `GET /api/pipeline-runs/:id/review-comments`: `{ comments, batches }` of one scope's review comments (`dataDir/review-comments/<kind>-<id>.json`, written by `ReviewCommentStore`). Every store write (create, change, delete, mark sent, discard) signals its scope's topic through the store's `onChange` (`reviewChanged`), so the comment routes need no entry in `liveWriteSignals`; deleting a session or a run discards its comments. The session topic accepts the session id form of `validId` (up to 80 characters). The browser follows them with `useReviewComments` (`web/features/review/`), whose writes await `written()`; the 30 s fallback poll runs only while the socket is down. A pipeline gate action with `review: true` (**Retry with feedback**, **Return for repair**, a group member's feedback) has the engine build the batch from the run's open comments against the whole-run diff (`server/features/pipelines/review-feedback.js`) and, once the action ran, mark the carried comments sent, which signals `pipeline.review:<runId>`. **Return to stage** on a finished run (`POST /api/pipeline-runs/:id/return-to-stage` with `review: true`, `server/features/pipelines/return-service.js`) does the same once the run reopened, and the reopened run's save pushes `pipeline.run:<runId>`. `GET /api/pipeline-runs/:id/diff` (the whole-run diff with its `fingerprint`) has no topic of its own: the browser reads it again when a `pipeline.run:<id>` push changes the run's status, current stage, attempt count or waiting group members, and on the manual **Refresh changes**; views of the same run share one read (`web/features/pipelines/run-diff-reads.js`).
- **Changes topic.** `session.changes:<sessionId>` is an owner-only state topic (`server/features/changes/live-topics.js`) whose value is the answer of `GET /api/sessions/:id/changes` (`SessionChanges#summary`, `server/features/changes/session-changes.js`): whether the session directory is a Git repository, its start commit, and each listed workspace (the session's toplevel and the worktrees under the repository's `.worktrees/`) with its diff base and changed files, added and removed lines. The working tree announces nothing and there is no file watcher, so the server samples the topic every 60 s (`CHANGES_SAMPLE_MS`) while a visible tab watches it and reads it at once on every `native-activity` chat event of the session (an agent turn starting or ending); a digest-equal read sends nothing. Each read runs `git rev-parse --show-toplevel`, `git worktree list`, the default-branch lookup (`origin/HEAD`, else a local `main` or `master`), and for every listed workspace its base (`git merge-base` or the start commit, each checked with `exactCommit`), `git diff --numstat`, `git ls-files --others` and a line count of each untracked file (asynchronous Git calls, 30 s timeout each), so the cost scales with visible sessions and workspaces, not with idle ones. Each workspace also carries a `fingerprint`, a short hash over the numstat output and the size and mtime of every changed and untracked path, so an edit that keeps the counts still changes the value and the open diff is read again. The browser's 60 s fallback poll runs only while the socket is down. A session started before start commits were recorded records HEAD on its first summary read; the API answers it as `startCommit.source: "first-open"` (stored as `startCommitSource`). Login and pipeline sessions record no start commit, and the browser follows no topic for a login session. At session start, the HEAD read gives up after 5 s (`START_COMMIT_TIMEOUT_MS`), because creation runs inside the global serial barrier. `GET /api/sessions/:id/changes/diff?workspace=<id>` answers one workspace's parsed diff (bounded at 1 MB, `truncated`); the id must be one listed now, otherwise 404, and is never used as a path.
- **Ticket topics.** `tickets.project:<projectId>` and `tickets.connections` are owner-only state topics (`server/features/tickets/live-topics.js`). `tickets.project` carries `GET /api/tickets/projects/:projectId`: the project's source links (GitHub repository and label, linked Plane project) and its ticket start records with their write-back state, read from local data only. `tickets.connections` carries `GET /api/ticket-connections`, the Plane connections without their API keys. `TicketService` signals them after every write of its own: a source change or a start (once when it is recorded, again when the write-back ends) signals the project, and a connection change signals `tickets.connections` and every `tickets.project` instance, whose view names the connection. `RepositoryStore` signals every `tickets.project` instance when a GitHub token profile is created, updated (including the host default) or deleted, or a clone records a project's profile; a changed git remote is not watched and needs **Refresh**, which re-reads the topic and the list. This is server polling of the forge, not browser polling: the browser never polls the queue and only follows the topic. Each pass reads every connected source of a project once and appends new matches through `TicketSequenceService.appendFromRule` inside the queue's lock. The browser never polls the rules and only follows the topic. See [Ticket sources](ticket-sources.md#label-rules).
- **Rebuild topics.** `craft.rebuilds` and `craft.rebuild:<id>` are owner-only state topics (`server/features/craft/live-topics.js`). `craft.rebuilds` carries `GET /api/craft/rebuilds`: the rebuilds, the owner's defaults, the eligible Claude accounts, the stacks and whether Craft Anything is installed; `craft.rebuild:<id>` carries `GET /api/craft/rebuilds/:id` (`{ rebuild: null }` once it is gone). `CraftRebuilds` signals them from its `onChange`, and the Craft Anything tool's `onChange` signals the list. While a rebuild runs, the supervisor samples Craft Anything every 2 s and signals the topic only when the rebuild's view changed; nothing is sampled while none runs. The page's activity is read when the view changes, not on a timer ([Rebuilds](craft.md)).
- **Limits.** Client frames are at most 4 KiB: a larger one closes the socket with 1009 (`ws` `maxPayload`), any other malformed frame with 1008. A socket holds at most 64 subscriptions (`error` with code `limit`) and may send 600 `sub` and `unsub` frames a minute (`SUBS_PER_MINUTE`, a token bucket that refills evenly): every `unsub` of a topic's last subscriber drops its instance and the next `sub` reads it again (a file topic also watches anew), so a client that loops would churn without end, while a page load or a view change sends a few dozen. A `sub` over the limit is answered like a full socket, `error` with code `limit`, and drops the topic if the socket held it; the browser then polls the topic's REST route, as for any refused topic, until it reconnects. An `unsub` takes a token but is always honoured, since it only frees. A frame over the topic's `maxBytes` (256 KiB by default, 1 MiB for `state`, whose sessions take about 1-3 KiB each, for `pipeline.run`, whose execution log has no bound, and for `agent.list`, the former event stream's limit) is sent as `stale`, at most once per 10 s per subscriber (`STALE_QUIET_MS`): a value that stays too large would otherwise send every tab to its REST route on every change, and a `stale` due within the window is sent once at its end unless a frame that fits arrived meanwhile. A rows subscriber holds no baseline after `stale`, so its next frame is a snapshot, and once one fits again it is back on deltas. A reader that falls behind keeps only the newest frame per topic above 256 KiB buffered and is closed with 1013 above 2 MiB. A closing server ends the sockets with 1012.
- **Presence.** A visible, focused tab reports its route with `{op: "presence", route}` (`web/features/notifications/usePushPresence.js`), which holds web pushes about that view exactly as `POST /notifications/presence` does. The owner reports without a scope, a restricted user in her own (as `POST /me/notifications/presence`), so a socket never reports for another person. A route over 512 characters is ignored, a non-string route is malformed (1008), and a socket may send 60 presence ops a minute (the service also limits each person to 120 a minute across sockets and REST). The tab uses the channel only while it is open; while it is down or in fallback mode, and when no topic keeps it open, presence goes over REST.
- **Fallback.** The client (`web/lib/live/live-client.js`) reconnects with backoff (0.5 s doubling to 30 s) and resubscribes with what it holds, so a reconnect costs no REST read. After three handshakes in a row fail (a proxy without WebSocket upgrade, for example), `useLiveTopic` polls each topic's REST route at its former interval (`web/lib/live/live-topics.js`), only while the tab is visible, and keeps retrying the socket. A topic the server refuses is polled the same way. After a 1008 close the client checks `GET /auth/status` once, so an expired login shows the sign-in.
- **Hidden tabs.** A hidden tab unsubscribes the sampled topics (`session.requests`, `session.models`, `connections.problems`, `runtime.updates`, `job.operation`, `job.rea`, `job.ssh-tools`, `session.reload`, `session.changes`, `agent.reminders`, `agent.pinboard`, `agent.senders`, `operations.release-sessions`, `me.reminders`, `system.status`, `system.status.details`, `account.auth`) at once, so the server stops reading the screen for it; `state`, `inbox` and `agent.list` keep coming. A hidden tab sends no REST request: the fallback polling and one-time reads wait until it is visible. After five minutes hidden, or on `pagehide`, the socket closes and reconnects when the tab is visible again.

## Owner inbox

`server/features/inbox/` merges what waits for the owner into one read-only list: the request broker's open native requests of running sessions (`listAll()`, without the side effects of the per-session list), pipeline runs in `awaiting-human`, agent actions in `awaiting_approval` and team proposals. `OwnerInbox` recomputes the list when a source announces a change (broker events, pipeline `onChange`, agent `change` events) and on a timer while the live `inbox` topic has a subscriber, raises its revision only when the waiting set changed, and pushes the whole list on the owner-only live `inbox` topic (`server/features/inbox/live-topics.js`). Answers never go through the inbox; the page reuses each source's card and endpoint. Stale item addresses are resolved from the audit log for 24 hours. See [inbox](inbox.md).

## Persistence and safety boundaries

The configured data directory is private to the host user. Temporary application fixtures use their own home, data directory and tmux socket. Same-origin request checks protect browser mutations; untrusted archive, path and configuration inputs pass explicit feature boundaries. Profile separation is configuration isolation, not an operating-system sandbox: native CLIs still run with the host user's file permissions. A session may opt in to nono confinement instead: `server/features/nono/` owns detection, sandbox-profile listing and the adapter that composes `nono wrap` around the CLI, and every other launch adapter declares the grants that confinement needs by appending to the launch description's own grant list. That confinement is partial by construction; see the [sandboxing guide](sandbox.md) for the grant model and its known limitations.

Codex is the exception: it runs inside its own sandbox and defaults to `read-only`, which silently discards additional writable roots. A session that grants the per-session chat attachment directory through `--add-dir` therefore also pins `sandbox_mode="workspace-write"`, so the grant is real rather than merely requested. The YOLO launch mode already runs without a sandbox and is left as the operator chose it.

Managed Codex accounts pin `cli_auth_credentials_store` and `mcp_oauth_credentials_store` to `"file"`. Account creation seeds both in the account's `CODEX_HOME/config.toml`, every managed launch repairs them there, and every Codex process of a managed account (sessions, logins, status probes, history and plugin commands) also passes both as `-c` overrides, which outrank a trusted project's `.codex/config.toml`. The owner's local `~/.codex` stays unchanged. Codex's default store prefers the macOS keychain, whose entries are not scoped by `CODEX_HOME`, so ChatGPT logins and MCP OAuth tokens of managed accounts now stay inside the account profile. An MCP OAuth login that a managed account stored in the keychain before this pin must be repeated once in that account. The old keychain entry (service `Codex MCP Credentials`) stays usable only by the owner's local Codex, which may then use another account's token for the same server; remove it in Keychain Access or with `codex mcp logout <name>` in the owner's profile.

External top-level navigation is allowed only for known HTML routes with `GET`, navigation mode and document destination. WebKit's tested click navigation omitted `Sec-Fetch-User`, so that optional activation signal is not a prerequisite for opening the application. Cross-site API/subresource/frame access and mutations retain their checks. See the [Fetch Metadata specification](https://www.w3.org/TR/fetch-metadata/); the browser suite verifies the observed behavior in Chromium and WebKit.

Reuse shared path/configuration and shell/TOML serializers rather than adding ad hoc quoting or prefix checks. Never put credentials into process arguments, URLs, public metadata or logs. Preserve structured native configuration when adding temporary integrations.

## Verification

`npm run check` combines lint, formatting, file size, backend strategies and production build. Browser tests run against an isolated application by default. Property failures record reproducible seeds and shrink their examples. Platform and browser CI matrices are defined in `.github/workflows/verify.yml` (pull requests and merge queue), `webkit.yml` (WebKit: nightly and labelled pull requests) and `full.yml` (nightly and release); a configured matrix is not evidence that an unexecuted platform passed. See [testing](testing.md) for commands, fixture ownership and the limits of native compatibility checks.

### Project and session SSH accesses

`server/features/ssh/` owns reusable keys, pinned hosts, project bindings and explicit session grants. Project identity resolves Git worktrees through their common repository and ordinary directories through their canonical filesystem identity. The session separately persists the launch directory's path, device and inode; each project operation revalidates that binding. Shell `cd` cannot switch authority. Effective hosts are the current union of inherited project hosts and explicit assignments, so existing sessions see project changes without copying grants. This is API convenience scoping under one OS user, not an OS sandbox.

One application-owned SSH management service serializes metadata mutations through a private local RPC socket and the application mutation barrier. UI and MCP share this service. A versioned `ssh/catalog.json` atomically publishes keys, hosts, projects and persistent mutation receipts. Key validation/generation prepares isolated files before publication; rollback and startup recovery remove proven unpublished artifacts. Receipts bind project, operation and request ID to current resources. Deletion and reassignment tombstone all affected receipts, preventing replay from recreating data. New growth is limited to 16 MiB without evicting receipts or blocking deletion.

Startup migration preserves legacy resource IDs and explicit grants with global ownership. A durable cutover marker coordinates initial capability revocation, catalog publication and archival of the old active JSON files. The first migration requires CLI reload; ordinary service restarts preserve compatible capabilities. Old and new writers cannot share a data directory, and installations using this format cannot downgrade to releases without unified-catalog support. SSH files, catalog receipts and grants remain excluded from application backups.

Session MCP exposes project key generation, bounded local-path import, public-key discovery, unverified host scanning, independently pinned host registration and connection tests, alongside host listing and execution. Import preserves the source and returns only public metadata; encrypted keys and managed identity sources are rejected. Existing authorized SSH access or a provider workflow supplies bootstrap access. Scanning is not verification, and AgentPier does not install remote authorized keys automatically. Editing, deletion and reassignment remain owner UI operations. Ordinary HTTP results and all MCP results contain public metadata; a separate authenticated owner POST downloads an unencrypted private key from an already-open validated descriptor.

Each SSH invocation captures one endpoint, username, identity and pin revision with an execution-specific known-hosts file. MCP checks effective grants and the revision before spawn and during execution. `server/ssh.mjs` resolves the same effective access for the manual helper; already-started manual connections may continue after revocation. Codex/Claude startup hooks and the OpenCode context plugin compose SSH discovery with Memory, AgentBus and existing user configuration, including zero-host projects. Login/headless sessions remain excluded; shell sessions receive manual access without a model hint. See [SSH accesses](ssh-access.md) for provisioning, reload and storage details.

Plain OpenSSH in sessions runs through one SSH agent per eligible session, served by `SessionSshAgents` (`server/features/ssh/ssh-session-agents.js`) in the AgentPier process. `ssh-agent-protocol.js` and `ssh-agent-keys.js` speak the agent protocol and verify `session-bind@openssh.com`; `ssh-agent-policy.js` decides each signature (bound host key, user and key of a currently granted host, no forwarding, legacy rules); `ssh-agent-socket.js` serves the socket under `~/.agentpier-ssh` and `ssh-agent-audit.js` writes `ssh.connected` and `ssh.denied`. `ssh-session-config.js` writes the session folder `<dataDir>/ssh-agents/<session id>` (aliases, `ssh_config`, `known_hosts`, public keys and the `bin/` wrappers), and `ssh-agent-launch.js` adds the environment and sandbox grants to the launch. The session lifecycle prepares the agent after the SSH integration and discards it on stop; reload keeps the token and socket path with a new generation, a service restart restores running agents, and shutdown closes listeners but keeps the folders. A committed catalog change (`SshCatalog.onPublished`), an assignment change and a project rebind resync the files. `ssh-user-config.js` and `ssh-user-config-sync.js` keep the marked block in `~/.ssh/config` and the dispatcher `<dataDir>/ssh-agents/include.conf`, checked with `ssh -G` after every write. Browser responses carry only `sshAgent.enabled` (`publicSession`); the dialog follows the `job.ssh-tools` live topic, which carries the agent status and aliases.

Agents with shell get the same through one SSH agent per eligible agent. Sessions and agents share one `SshAgentRegistry` (`server/features/ssh/ssh-agent-registry.js`): it holds every live socket of both kinds by owner (`{ kind: "session" | "agent", id }`), writes the owner's files, keeps tokens unique across both kinds, feeds the one `include.conf` and is the single change channel (`listen(kind)`). `SessionSshAgents` is its session adapter; `AgentShellSsh` (`server/features/assistants/agent-ssh-shell.js`) is the agent adapter. It reconciles the eligible agents (shell not off, an SSH grant of any mode, not a user agent, not archived, personal or a temporary member using its lead's SSH) on every agent event and catalog publication, authorizes each signature against the holder's live `trusted` grants, keeps each agent's folder under `<dataDir>/ssh-agents/_agents/<agent id>` with `shell-env.sh` and a `state.json` token, and reports `status(id)` (`ready`, or `unavailable` with `no-shell`, `no-hosts`, `no-openssh`, `openssh-too-old`, `failed` or `not-eligible`). `server/application/agent-ssh-shell-wiring.js` creates it with the agent feature, sets the config hooks `sshShellPath` and `plainSsh` (the turn's instructions list the aliases) and signals the `agent.ssh-agent` topic. The agent's `bin/` joins `tools.exec.pathPrepend` after the GitHub folder; the Gateway's exec shell (`exec-shell.js`) sources its `shell-env.sh` only under the literal agents root; `exec-approvals.js` resolves programs against the same order, and `exec-ssh-wrappers.js` lets **Always allow** write a program entry for the agent's own `ssh`, `scp` and `sftp` wrappers. Agent audit rows carry `details.assistantId` and `source: "system"`; `connection-last-use.js` counts them for **Last used** (cover part `agentPlainSsh`).

Agents reach SSH through the `agentpier_ssh` tool of the `agentpier-teams` plugin, not the session MCP server. The loopback team bridge binds the call to the agent's ledger attempt (or, without one, to a bound routine's run session) and hands it to `AgentSsh` (`server/features/assistants/agent-ssh.js`), which runs the command in the AgentPier process through `SshAccessStore.connection()` and `ssh-run.js`. Grants live in `assistant_access.body.sshAccesses`; approvals and trusted runs are `assistant_actions` rows; `SshManagement.removeHost` revokes agent grants before the catalog changes.

Email grants live in `assistant_access.body.mailAccesses` as `{ accountId, level: "read" | "send", recipients }` (`server/features/assistants/mail/agent-mail-grants.js`). Only the owner's own agents and permanent team members hold them; user agents, temporary members and agents with their own Telegram bot for other people are refused on the server. `MailAccountStore.remove` revokes every agent's grant for the account before the catalog changes (`AssistantAccess.revokeMail`).

`server/features/mail/` owns the owner's IMAP/SMTP accounts and every mailbox operation: `MailAccountStore` keeps `mail/accounts.json` and one owner-only password file per account through `SshPasswordStore` (`mail/passwords/`), binds a saved password to the account's hosts, ports and security, and opens one `imapflow` connection or `nodemailer` transport per call with certificate validation and TLS 1.2 or newer (`mail-connection.js`, errors reduced to `MAIL_*` codes). The other modules list, read and search within fixed bounds, flag, move (MOVE only, never expunge), save drafts and compose messages; `mail-backup.js` seals the accounts into passphrase backups. `server/http/routes/mail.js` is the owner-only route. Agents reach mailboxes through the `agentpier_mail` tool of the `agentpier-teams` plugin: the team bridge hands the call to `AgentMail` (`server/features/assistants/mail/`), which checks the turn's origin class, the live grant and the recipient rules, and keeps sends that need the owner as `mail_send` rows in `assistant_actions`. The web side is `web/features/mail/` (Connections › Email accounts) and the Access tab's `MailAccess.jsx`, `MailGrantPage.jsx` and chat cards `MailApprovalCard.jsx` and `MailRunNote.jsx`. See [Email for agents](mail.md).

SFTP hosts are a second host type in the same catalog (`sftpHosts`, so a release without SFTP keeps its SSH list). `server/features/sftp/` holds the in-process `ssh2` client (host-key pinning, password or key sign-in, no `sshpass`), confined remote and local paths, transfer planning with a plan digest, and `SftpJobs`, the cancellable background jobs. Coding sessions reach them through the `sftp_*` tools of the SSH MCP server (`sftp-session-tools.js`), agents through the SFTP actions of `agentpier_ssh` (`agent-sftp*.js`: policy, runs, approval cards, grants and Telegram notices). Passwords are kept by `SshPasswordStore` under `ssh/passwords/`. See [SFTP access](sftp-access.md).

Agents hand the owner files through the same plugin's `agentpier_share_file` tool: the bridge binds it to the ledger attempt, a routine's or hook's run, or, for any other run of the owner's chat, to that chat (`owner-shares.js`), and hands it to `AgentShares` (`server/features/assistants/agent-shares.js`), which reads the file from the agent's workspace (`agent-share-source.js`), stores the copy outside the workspace (`agent-share-store.js`) and, for a Telegram turn, queues a `file` notice in the channel outbox. See [Files agents share](assistant-gateway.md#files-agents-share-2026-10-17). The same plugin's `agentpier_pinboard` tool keeps the owner's pinboard (`agent-pinboard.js`, SQLite tables in `agent-pinboard-store.js`): its entries are links, not copies, and every owner read (`agent-pinboard-view.js`, `agent-pinboard-files.js`) validates the path again with the share rules and streams the bytes from the checked descriptor. See [Agent pinboard](assistant-gateway.md#agent-pinboard-2026-11-07).

## Agents (managed OpenClaw)

Agents are optional. While they are switched on, AgentPier supervises one pinned
OpenClaw Gateway per host as the same OS user and talks to it over authenticated
loopback WSS with a pinned certificate. The browser never reaches the Gateway
directly.

- `server/features/assistants/`: AgentPier's runtime lifecycle (`runtime-updates.js`
  with its snapshot, blockers and retention, `pending-restart.js`, `runtime-paths.js`).
  The OpenClaw adapter, `runtimes/openclaw/`, holds the configuration compiler
  (`openclaw-config/`, `runtime-config.js`), the runtime manifest, its
  dependency lock (`runtime-lock/`), installation (`runtime-install.js`,
  `runtime-provisioning.js`), the Doctor migration (`runtime-doctor.js`), the
  supervisor (`runtime-supervisor.js`, with `gateway-log.js` and
  `gateway-ownership.js`) and the Gateway transport (`gateway-client.js`,
  `gateway-protocol.js`, `gateway-tls.js`). The compiler writes locked paths and AgentPier-owned
  settings, plus only the allow-listed overrides from the advanced settings
  (`advanced-config.js`). The same directory holds agent profiles and conversations,
  capabilities and skills, shell approvals and the allowlist, teams (`team-*.js`, with the bundled `team-plugin/`), lead requests
  (`lead-request*.js`), agent SSH access (`agent-ssh*.js`), reminders, routines and check-ins (`native-*.js`) and chat
  attachments (`agent-attachments.js`, chunked videos in `agent-video-*.js`, the owner's
  usage, clear and verified folder removal in `agent-attachment-storage.js`, a Hermes
  agent's per-chat folders in `chat-file-folders.js` and their move from `attachments/`
  in `chat-file-migration.js`).
- `server/features/assistant-channels/`: Telegram pairing, ingress, delivery and the
  durable outbox, and agents' own bots for other people (`telegram-senders.js`).
- `server/features/mcp-servers/`: the central MCP server store, bindings to agents and
  to the coding CLIs, and OAuth logins (see below).
- HTTP routes live in `server/http/routes/assistant*.js` and `mcp-*.js`.

Feature code is moving behind an agent runtime port, so that agents can later run on
another runtime than OpenClaw. `server/features/assistants/runtimes/agent-runtime.js`
names the sub-ports (`host`, `sessions`, `events`, `agents`, `agentFiles`, `config`,
`approvals`, `routines`, `skills`, `browser`, `models`, `channels`) and the
`capabilities()` shape (per capability `available`, plus a reason id when it is not);
`runtimes/runtime-for.js` resolves the runtime of an agent, today always the OpenClaw
adapter in `runtimes/openclaw/`, which is the only place meant to call the Gateway
client. The adapter's `host` sub-port wraps the supervisor: `ready()`, `status()` with
the supervisor's availability states, `version()`, `subscribe()` and `start`/`stop`/
`restart`, plus `connection()`, a handle that changes when a restart replaces the
Gateway client; feature code checks readiness with `hostReady()` and compares
`hostConnection()` across an await, both from `runtime-for.js`, instead of reading
`runtime.client`, and starts, stops and reads it through `hostOf(supervisor)`. The
host also installs (`install`, `sameInstall`), reports the shipped version and
whether an install record is it (`target`, `current`), stages an update in the
background after an AgentPier update (`stageUpdate`), migrates the stopped state to a
new version (`migrate`), stops a leftover migration and clears its files before a
rollback restores the snapshot (`stopMigration`, `clearMigration`) and tells whether
a saved change needs a restart and which start loaded the running configuration
(`restartNeeded`, `generation`). AgentPier's own update journal (`runtime-updates.js`:
staging, maintenance, snapshot, validation, rollback, recovery) and the pending
restart (`pending-restart.js`: why a restart waits) stay outside the adapter and use
only these methods; the OpenClaw side is `runtimes/openclaw/openclaw-lifecycle.js`. The `sessions` sub-port creates, sends to, aborts, waits for,
describes, lists, keeps open, compacts and deletes agent sessions, reads their history
and downloads generated artifacts, with named parameters; `sessions.on(connection)`
binds those calls to the connection a caller captured before an await, so they never
reach a Gateway that replaced it; OpenClaw's session-create
retries and native-archive handling (`session-create.js`, `native-chat-archive.js`)
live in the adapter. The `events` sub-port delivers normalized run events of the
current connection (`started`, `text`, `tool`, `finished`, `aborted`, `failed`
with a reason, and approvals passed through), each with OpenClaw's frame name and
payload alongside: reply text, tool steps (`run-steps.js`) and approval details are
still read from that payload. The `agents` sub-port lists, creates, updates and
deletes the runtime-side agent, waits until a new one is listed and reports which
agents the current connection refused to admit; the `agentFiles` sub-port reads and
writes an agent's workspace files over their expected hash and searches its memory;
the `config` sub-port reads the live configuration with its hash, looks up whether a
path reloads without a restart, applies a change built from the current
configuration and watches until the Gateway adopted it. The `approvals` sub-port
lists pending shell approvals, sends the owner's answer, reads how requests ended,
reads and writes the exec allowlist over its hash and plans what "Always allow"
writes when OpenClaw withholds it (`exec-allowlist-policy.js`, which reads
OpenClaw's interpreter, wrapper and package-manager lists); approval requests still
arrive as run events. The `routines` sub-port drives OpenClaw's cron scheduler: it
lists an agent's jobs page by page, adds, changes, removes and runs a job (a forced run
answers whether it was queued or refused), lists a job's runs and reads whether the
scheduler is on. Callers hand and receive AgentPier's own routine model
(`routine-definition.js`: schedule, prompt, the agent, target, delivery, enabled,
marker and run state); the adapter translates it into the cron jobs AgentPier
always submitted (`openclaw-routine-jobs.js`) and tells which routine run a
session key belongs to (`routines.runOf`), so no caller parses OpenClaw's
`agent:<id>:cron:` keys. The `skills` sub-port reads an
agent's skill status (`skills.status`) and tells a refusal for an agent OpenClaw has
not created yet; the `browser` sub-port makes one call of OpenClaw's browser control
API (`browser.request`) and opens the live view's screencast socket; the `models`
sub-port reads the ChatGPT model catalog, signs accounts in through OpenClaw's login
wizard, probes and signs them out. `sessions` also asks the team plugin whether a
session still runs background commands and for a generated chat title, and the
`host` sub-port tells whether a captured connection still takes calls
(`connected`) and when it drops (`onDisconnect`), which the ChatGPT sign-in follows.
Each has `on(connection)` like `sessions`. OpenClaw's admission wait (`agent-admission.js`), the serialized
configuration writes (`live-patch.js`), the adoption watch (`config-adoption.js`)
and the roster wait (`agent-roster.js`) live in the adapter, and so does the
compiler in `openclaw-config/` that produces the configuration it applies.
`tests/unit/runtime-port-rules.test.js`
fails when server code outside `runtimes/` names a Gateway method in
`.call()`/`.request()` or reaches `runtime.client`. Every caller has moved behind the
port, so the rule is absolute: there is no allowlist, and no file outside `runtimes/`
may offend. A third rule refuses imports of adapter modules from outside `runtimes/`:
only `runtime-for.js` and `agent-runtime.js` are public. Composition roots
(`server/application/assistant-graph.js`, `services.js`, `*-wiring.js`) may construct
the OpenClaw supervisor; a shrink-only allowlist names the two modules that still read
OpenClaw's runtime manifest (the MCP toolchains share its Node pin, and the team
plugin installer checks its versions until the team plugin moves into the adapter). `tests/helpers/runtime-port-contract.js` is the contract every adapter
passes, every sub-port included.

The config sub-port carries the compiler as `config.compiler`
(`runtimes/openclaw/openclaw-compiler.js`); `compilerFor(agent)` in `runtime-for.js`
picks it from the runtime registry by the agent's runtime and returns the same object
without a host. Feature code reaches every compile step
through it: a Gateway start, an agent's live entry and its readback, the live MCP,
Telegram allowlist, browser profile and dreaming patches, the web tools signatures,
skill shadows, the advanced settings allow list and the CLI's process environment.
What the stores hold in AgentPier's own terms stays outside the adapter:
`mcp-servers/mcp-inputs.js` (MCP eligibility, the per-agent name of a placeholder
server, the store inputs), `assistant-channels/telegram-inputs.js` (which agents may
own a bot, the bot store inputs), `assistants/browser-profile-names.js` and
`assistants/agent-folders.js`.

The compiler reads AgentPier's runtime-neutral desired state
(`assistants/agent-desired-state.js`, ADR 0006 decision 3). Per agent it names the
tools it may hold as grants with what each needs of the runtime, its shell level and
PATH folders, memory, skills, MCP bindings, web capabilities, browser, whether it
may own a Telegram bot for other people, its SSH grant and team membership, and for a
live apply its instructions and model connection; for the host it names the team
plugin, native tools, web tools, MCP servers, Telegram bots and dreaming. The
composition root builds it from the stores for every Gateway start, and the live
applies (`assistant-config.js`, `mcp-changes.js`, `telegram-senders.js`,
`browser-profile-sync.js`) build it for theirs; `config.apply`, `config.applyModel`
and `config.applied` write and read back one agent. OpenClaw-only settings stay in
the adapter: advanced settings are the `advancedSettings` capability with
`config.compiler.advancedSettings`, a runtime without them lists none and refuses a
save. Hermes maps the ones it has an equivalent of by setting id
(`runtimes/hermes/hermes-config/advanced.js`) from the same stored overrides. `tests/unit/openclaw-config-golden.test.js` holds the compiled
`openclaw.json` of representative agents byte for byte.

See [the user guide](agents.md), [the Gateway design](assistant-gateway.md) and
[ADR 0002](adr/0002-managed-openclaw-assistants.md). The proposed
[runtime port](adr/0006-assistant-runtime-port.md) moves this coupling behind one port so
that agents can also run on Hermes Agent.

## Central MCP servers in the coding CLIs

`server/features/mcp-servers/` writes servers bound to Claude Code, Codex or OpenCode
into each CLI's native configuration before every session start and on every save. It
records the entries it wrote by name and SHA-256 hash, changes only entries that still
match, and offers entries found in the CLIs for adoption. See
[MCP](mcp.md#central-mcp-servers-in-the-coding-clis).

## Artifacts

`server/features/artifacts/` stores private static pages published by sessions and
agents through the `artifact_publish` MCP tool and shows them in a sandboxed viewer
without scripts. See [artifacts](artifacts.md).
